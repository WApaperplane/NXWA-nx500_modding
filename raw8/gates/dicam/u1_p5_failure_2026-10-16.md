## 2. 决定性诊断：systemd 内存里那份 unit 是旧的

```
# 修复前后对比（同一条命令）
systemctl show di-camera-app | grep -c ExecStartPre          →  0     ← 开机后的状态
systemctl daemon-reload ;  echo rc=$?                        →  rc=0  ← 安全操作，无 restart
systemctl show di-camera-app | grep -c ExecStartPre          →  1
  ExecStartPre={ path=/opt/usr/nx-ks/dicam/t2_premount.sh ; ... start_time=[n/a] ; pid=0 ; status=0/0 }
```

`systemctl status` 旁证：

```
Active: active (running) since Wed 2016-03-30 17:08:43 KST; 10 years 6 months ago
Mar 30 17:08:43 drime5 systemd[1]: Started Start di-camera-app.
Warning: Unit file changed on disk, 'systemctl daemon-reload' recommended.
```

⇒ **systemd 从未重读这个 unit**（它加载的那份没有 `ExecStartPre`）。

### 2.1 排除「文件问题 / 命名空间问题 / 解析问题」

| 假设 | 检验 | 结论 |
|---|---|---|
| 文件被写坏 / CRLF / 缺 bash | `tr -cd '\r' \| wc -c` = **0**；`od -c` 行尾 `h \n`；`/bin/bash` 在 | ✗ 排除 |
| 我看的文件 ≠ PID 1 看的文件 | 我方视图 vs `/proc/1/root/...` vs `/proc/247/root/...`：**md5 全同** `b227c619f4220ed6f30dcca62ae1a4ab`，size=371 inode=43 mtime/ctime=18:07:40 | ✗ 排除 |
| 老 systemd 的 `show` 不支持 ExecStartPre | 同机 `ac.service` 的 `show` **正常列出** ExecStartPre（含 pid/status） | ✗ 排除 |
| 文件在本轮开机中被改过 | `stat` 的 **ctime = mtime = 18:07:40**（ctime 无法被 `cp -p` 保留）⇒ 自 18:07 起未被写过 | ✗ 排除 |
| ExecStartPre 执行了但静默失败 | 若在内存里，`show` 会列出（`start_time=[n/a]`）；实测**连条目都没有** | ✗ 排除 |

### 2.2 反向确认：App 确实是**被重新 exec** 的

```
systemctl show di-camera-app（reload 前）:
  ExecStart={ path=.../di-camera-app ; start_time=[Wed 2016-03-30 17:08:43] ; pid=247 }
  ExecMainStartTimestampMonotonic=12270778      ← 微秒 ⇒ boot+12.27s
  UserspaceTimestampMonotonic=1432378           ← 微秒 ⇒ userspace boot+1.43s
/proc/247/stat 第22字段 starttime = 1224 拍     ← boot+12.24s（HZ=100）
```

⇒ App 在本次开机 **boot+12.2s 被 fork/exec**（与 10-13 记录的 `App exec = boot+12.2s` 完全一致），
但用的 unit 定义是**旧的** ⇒ **P5 的语义（"挂载先于 App exec"）在本机不成立**。

## 3. 机制：本机是「内核冷启 + 用户态恢复」的休眠机型

| 证据 | 值 |
|---|---|
| `/proc/cmdline` | `... hibernate=nocompress ... noresume ...` |
| `/sys/power/bootmode` | **2**（`hibernation.sh` 里 `4` = bootshell cold-boot） |
| `/etc/snapshot` | 存在（4 字节 NUL，标记文件） |
| `/usr/bin/hibernation.sh` | 保存侧：zram swap + `mkswap /dev/mmcblk0p9`（**p9 当 swap 装镜像**）+ 末尾 `mount -o ro,remount /` + `touch /tmp/.hib_ready` |
| `/usr/bin/hib_exjob`、`hib_tool`、`hib_tmp.sh`、`/usr/sbin/hib_gui.raw` | 休眠/恢复作业组 |
| `/tmp/.hib_ready` | mtime **Mar 30 2016**（tmpfs） |
| `/tmp/.hib_post` | mtime **Oct 16 19:04**（= 本次开机产生 ⇒ 恢复/后处理步骤在本次开机跑过） |
| 时钟 | 开机早期读数为 **2016-03-30 17:08:38**（镜像时间），开机中某刻才校正为 2026-10-16 ⇒ 这解释了所有 "2016-03-30" 时间戳 |

**推论（高强度证据，但非最终证明）**：本机正常开机走的是**用户态恢复路径**——内核对上电是新的（`uptime` 复位、`noresume`），而 **PID 1 的内存状态（含已解析的 unit 表）被恢复**，所以 systemd **不会重读 unit 文件**；随后由恢复链把 App **重新 exec**（12.2s），此时用的就是那份**旧 unit**。

**工程结论**：
1. **凡"改 unit / 依赖 systemd 每次开机重读配置"的投递方式，在本机上都不成立**（P5 阵亡；P1/P2 早就排除）。
2. 要在 App exec（+12.2s）之前落地，投递点必须落在**恢复链**里（`hib_exjob` / 写 `.hib_post` 的那一环），或
3. 改用**就地落盘**（不需要任何钩子：因为 App 每次上电都会被重新 exec）。

## 4. 就地落盘的可行性核对（为下一步选项准备）

| 目标 | 位置 / 设备 | 可就地写？ | 备注 |
|---|---|---|---|
| App 二进制 C-2 | `/usr/apps/com.samsung.di-camera-app/bin/di-camera-app`，**dev=179:10（p10 rootfs）**，4,773,516B | ✅（`mount -o remount,rw /` 后写入；p10 余量 **23MB**，96% 已用） | 18:07 写 unit 就是这么干的（同一分区、已证可写）。App 每次上电重新 exec ⇒ **换文件即生效** |
| M2 locale `.mo` | `/usr/share/locale` 是 **squashfs**（`/dev/loop0` ← 文件 `/usr/share/usr_share_locale.squash`，位于 p10） | ⚠ 不能在挂载点内写；但**可以替换那个 squash 文件本体**（离线用 PC/WSL 重建 → 推回 → 下次开机挂载即生效） | 需 `unsquashfs/mksquashfs`（离线做）；p10 余量需容纳新文件 |
| 两者（备选） | 直接改 SLP 里的 p10 镜像（刷机式，T6-C1 同族流水线） | ✅ 但属**刷机（L4，唯一不可逆层）** | 与 "刷机不丢" 的目标一致（mod 随包分发） |

★ 注意权衡：**就地落盘会被"刷任何官方 SLP"覆盖**（这正是 10-15 选 P5+bind 的初衷：mod 件放 p14 刷机不丢）。
⇒ 若走就地落盘，需同时接受"每次刷机后需重装"或另做刷机包。
