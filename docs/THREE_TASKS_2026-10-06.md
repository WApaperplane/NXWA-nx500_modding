## 1. ★★ 关于花屏：这是重要诊断，不是失败

用户报告：**严重花屏，但不死机，半按快门对焦后恢复。**

### ★★★ 这恰好是"3D LUT 被真正启用"的证据
```
OSD 正常（图标/文字/参数都对）+ 图像区花屏
```
⇒★ **OSD（叠加层）与图像数据通路是分离的**。
⇒★ **OSD 正常 + 图像花屏 = 图像通路被改动，OSD 通路没被动**。
⇒ 这正是"3D LUT 已插入 ISP 数据通路"的预期表现 —— 若 LUT 通路没通，反而会**完全没变化**。

### ★★ 判读
| 现象 | 含义 | 是否符合预期 |
|---|---|---|
| 花屏 + 半按快门恢复 | LUT 数据格式/位数不对，硬件读到了垃圾 | ★ **符合预期**（identity 不该花屏）|
| 不死机 | 3D LUT 是**软状态**，触屏/快门重触发即可重载 | ★ **符合预期** |
| OSD 正常 | 只影响图像通路，不影响控制通路 | ★ 符合预期 |

⇒ ★★★ **这条信息把"花屏"从"失败"重新定义为"通路已通、格式待定"。**
⇒ ★ 与我此前的预判完全一致（identity 无变化 = 通路通；花屏 = 格式错）。

### ★★ 由此确定的排查方向
**格式问题，三个候选（按可能性排序）**：
1. ★★ **单通道 vs 三通道** —— 我倾向单通道（`load_lut` 的 `sel` 就是通道号），但**尚未实机验证**
2. ★★ **8-bit vs 16-bit** —— 实测缓冲 4913 = 17³×1 支持 8-bit单通道
3. ★ `SelCbCr_ch`(bits[1:0]) 取值 —— 我一律写 0

⇒ ★ **下一步最该做的**：先试**三通道逐个 load**（`sel`=0/1/2 各一次），
　因为若单通道假设错，一次 load 只填了 1/3 的表 → 未填区域是垃圾 → 花屏。

## 2. ★★ 任务 1：boot0 备份完成（10 → 11 分区）

### 发现
```
/proc/partitions:  179  15  4096  mmcblk0boot0     ← ★ 报4096 扇区
/sys/block/mmcblk0boot0/size:  8192               ← ★ 真值：4 MB
```
⇒ ★⚠️ **`/proc/partitions` 对 boot0/boot1 报的大小是错的**（少一半）。
只用它判断会备份不全。

### 已完成
| 项 | 值 |
|---|---|
| 设备 | `/dev/mmcblk0boot0` |
| 大小 | **4194304 字节（4 MB）** 完整 |
| 相机侧 MD5 | `ec406739bb8135bdd6c4c0681e55597b` |
| PC 侧 MD5 | `ec406739bb8135bdd6c4c0681e55597b` |
| 落点 | `raw8/emmcbak/boot0.bin` + 相机 SD `/mnt/mmc/_xfer/boot0.bin` |
| **校验** | ★★ **PASS（双向一致）** |

### ★★★ boot0 是什么（重要）
```
头部：07 00 00 ea 09 00 00 ea 09 00 00 ea ... fe ff ff ea ...
     = ARM 向量表（全是指令，非数据）
```
⇒ ★★ **boot0 = 第一级引导代码**（在 p7 之前的一环）。
⇒ ★★★ **改boot0 = 绝对变砖，且无任何退路。我们绝对不碰。**
⇒ 这也把"刷 p7 有多危险"彻底定性了：**p7 之上还有 boot0，p7 坏只是画面异常。**

对比 `boot1` 头部 = `90 f2 01 00 / 41 01 00 00 / 69 01 00 00 ...`
⇒ 偏移/长度表结构（非可执行代码）= 与记忆中"M4 = LCD+电源管理"一致。

### ★★ 顺带查出并解决的一个疑点：p1 与 p5 相同
```
dd if=/dev/mmcblk0p1 bs=1M count=1 | md5sum = 369065b925fab3cb8d77a9c8d978130e
dd if=/dev/mmcblk0p5 bs=1M count=1 | md5sum = 369065b925fab3cb8d77a9c8d978130e
```
⇒ ★★ **实机确认 p1(adj) 与 p5(pref_recovery) 整分区 20 MB 逐字节全等。**
⇒ ★ **不是备份脚本的缺陷**（原 MANIFEST 猜的是"可能是空的"，现在是确定结论）：
**三星出厂就把这两个分区刷成同一份数据**。恢复时任选其一即可。

MANIFEST 已更新（记录了 boot0、p1/p5 的确定结论、安全边界）。

### ★ 备份现状：11/11
```
boot0  boot1  p1  p2  p3  p5  p6  p7  p8  p12  p13   （合计189.2 MB）
```

★ **没有加 `-B`**（社区 README 自己标了 DANGER ZONE）⇒ **无密码 root 登录未开启**。

### ★★★★★★ 你最关心的那个问题：有确定答案了

> "不确定 SSH 在刷写固件的情况下能否使用，如果中途有问题，回写就很麻烦了"

**答案：能用，而且比我们预想的更安全。** 依据是官方分区表 `/etc/parttab`：

| 卷名 | 分区 | `image` 栏 | 刷官方固件时|
|---|---|---|---|
| **opt-usr** | **p14**（= `/opt/usr`，我们 mod 与 SSH 都在这）| **`none`** | ★★ **不被覆盖** |
| pref | p2（FilmLab 配方）| `none` | ★ 不被覆盖 |
| pref_recovery | p5 | `none` | ★ 不被覆盖 |
| adj | p1 | `none` | ★ 不被覆盖 |
| rtos_data | p8 | `none` | ★ 不被覆盖 |
| **rtos** | **p7（ISP）** | `rom.bin` | ★★ **被覆盖** |
| platform | p10（rootfs）| `rootfs.img` | ★★ 被覆盖 |
| bootloader | boot0 | `bootloader.bin` | ★★ 被覆盖（我们不碰）|

⇒ ★★★★★ **关键推论**：
1. ★★ **`/opt/usr`(p14) 的 `image=none` ⇒ 刷官方固件【不覆盖】它**
   ⇒ **mod、telnet、ftp、以及刚装的 dropbear 全部活着穿过刷机过程**
2. ★★ **`/opt/ssh` 与 host key 都在 p14** ⇒ SSH 身份在刷机后**不变**
   （host key 不变 ⇒ PC 端不会有 "REMOTE HOST IDENTIFICATION CHANGED" 警告）
3. ★ **`pref`(p2) 也不被覆盖** ⇒ FilmLab 配方存活（与之前观察一致）
4. ★ **`rtos`(p7) 被覆盖** ⇒ 这正是"官方退路能恢复 p7"的原因，**逻辑自洽**

### ★★ 由此得出的刷机安全流程
```
刷固件全程：
  SSH（p14，★ 不被覆盖）★ 唯一全程可用的加密通道
  telnet（p11/opt? 实际在 p14）★ 兜底，明文但本地可控
  ⇒ ★ 加密通道 + 明文兜底 两条都在，不需要依赖"刷完还能连"
恢复路径：
  ① dropbear 仍在 ⇒ 传文件、跑命令、读日志
  ② telnet 仍在  ⇒ 万一 SSH 有问题
  ③ 机身菜单 Firmware Update ⇒ 最终兜底（p7/rootfs 都可覆盖恢复）
```

⇒ ★★★ **结论：SSH 不但刷机时能用，而且它本身就是"刷机期间唯一不会被刷掉的管理通道"。**
⇒ ★ **之前担心的"刷机中途失联"不成立** —— 因为 `/opt/usr` 不参与官方刷写。

### ★★ 附带收益
| 项 | 收益 |
|---|---|
| ★ 11.5 MB p7 镜像 / SLP 整包 | ★ **SFTP 安全搬运**，不FTP（明文 + 我们踩过 CRLF 坑）|
| ★ 刷机后回读校验 | SFTP 拉回 md5 比对 |
| ★ 收窄攻击面 | 刷机期间可临时关 telnet/ftp ⇒ 只剩密钥端口 |

## 4. ⏸ 任务 3：dfmsd USB 文本协议 —— 建议暂缓，理由如下

社区线索（otto k，2016）：*"dfmsd daemon expects textual commands from the computer"*，
且 `info.tgw` 进 PTP 模式后 `gphoto2 --summary` 报 `PTP I/O error` + `VID/PID = 0x0,0x0`。

### ★ 为什么现在做收益低
| 理由 | 说明 |
|---|---|
| ★★ **SSH 已解决同一问题** | "安全通道"这个需求 SSH 完全满足，甚至更好 |
| ★ 不阻塞任何交付 | 导入 LUT、4 档切换、刷固件都不需要它 |
| ★ 成本未知 | `dfmsd` 是闭源 `di-camera-app` 的一部分，要逆它的 USB 文本协议 = 新一轮逆向 |
| ★★ **即使成了也只有"文件传输"价值** | 社区 10 年无人逆完（gphoto 都不支持）|
| ★★ **不影响刷固件安全性** | 刷机安全性已经由 `/opt/usr` 不被覆盖 + SSH 解决 |

### ★ 保留价值（若将来要做）
- ★ **USB 线传输大文件**（不依赖 WiFi，18 MB/s）—— 比 SFTP 走廊内快，但无加密
- ★ 可能解锁 USB 遥控拍摄（社区 issue #127 想做 webcam 直播）

⇒ ★★ **建议排在"导入 LUT 格式定案"之后**。理由：LUT 导入是当前主线且已通到收尾，
　USB 协议是支线且社区 10 年零进展。
