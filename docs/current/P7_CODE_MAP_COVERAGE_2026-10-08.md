## 1. 覆盖率定义（分子 / 分母，与旧口径的对应）

**分母恒为 `16466`** —— `ghidra/52_pseudocode_index.txt` 里 Ghidra 识别出的函数总数（与旧口径一致）。

**分子 = "有硬证据的身份（identity）" 的去重并集。** "身份"有两种：

| 身份 kind | 形态 | 含义 |
|---|---|---|
| `fun` | `FUN_xxxxxxxx` / `Reset` | 落在 Ghidra 函数表里的函数 |
| `addr` | `@<文件偏移>` | vtable 槽指向、但**不在** Ghidra 函数表里的地址（p7 带 MMU，VA = 文件偏移 + 0x80000000） |

**旧口径（记为 口径 O）** 直接用各 TSV 的**原始字符串键**做并集，于是 `p7_extend_map.tsv` 的
`ext` 列（**十进制**键，如 `1016692`）与 `p7_class_map.tsv` 的 `func` 列（**0x 十六进制**键，
如 `0x1796e8`）**永远不相等** —— 即使它们描述的是**同一个地址**。

实测：`ext` 全部 667 个地址 **都在** `cls` 的地址集合里 ⇒ 旧口径把 **667 个地址计了两次**：

```
口径 O 分子 = |mod(FUN_) ∪ cls(key) ∪ ext(key)|     = 7939  ⇒ 48.21%   ← 旧报告的数字
口径 D 分子 = |mod ∪ cls ∪ ext|（地址规范化去重） = 7272  ⇒ 44.16%   ← 真实基线
```

> ⇒ **48.21% 含有 667 条重复；去重后的诚实基线是 44.16%。** 两条口径在本文都给出。

## 2. 新增手段与各自的增益

| 通道 | 手段 | 增益（去重口径 D） | 是否有效 |
|---|---|---|---|
| **R** | **广义 RTTI**：typeinfo 的 **vptr 签名**校验 + 全镜像搜索 + 接受模板/嵌套名 | 7272 → **10294**（**+3022**，565 类 → 1047 类） | ★ 主力 |
| **P** | 函数指针表：连续 ≥4 个指向函数起点的 4 字节指针 | **+84**（10294 → 10378） | 有效（小） |
| **F** | 序言回收：被指针指向、有 ARM 序言的**漏识别函数** | 回收 **1115** 个函数（进统一口径分母+分子） | 有效（见 §3.4） |
| — | ~~Thumb 并入~~ | **0** | ✘ **无效**，见 §2.2 |
| — | 数据引用作第二通道（模块侧） | **0** | ✘ 见 §2.3 |

### 2.1 通道 R 的判据（本报告的核心）

Itanium ABI 的 `type_info` 结构 = `[vptr][name_ptr]`，其 `vptr` 指向 `__class_type_info`
家族（只有 3 个）的 vtable。于是判据是**三层校验**：

```
跳 1  某 4 字节字 W 指向一个字符串 S（S 就是类名）        → W 位点 = typeinfo.name（typeinfo+4）
跳 2  typeinfo VA 被某个数据字指向                        → 那是 vtable 的 typeinfo 槽（vtable-4）
      ★ 签名：typeinfo+0（即 vptr）∈ {规范 vptr 集合}
跳 3  从 vtable 起连读 0x8xxxxxxx 指针（遇非指针即停）     → 方法函数 → 文件偏移 → Ghidra 名
```

**规范 vptr 集合由数据自证**：用保守子集（长度前缀自洽的 910 个候选）统计 typeinfo+0，
发现它**只落在 3 个值**上：

```
0x80759908   0x80759ac0   0x80759b58      （文件偏移 0x759908 / 0x759ac0 / 0x759b58）
```

**自校验通过（最强证据）**：libstdc++ 自己的 RTTI 类被原样找回，且它们的 vtable 正好落在这 3 个地址上：

```
cls:N10__cxxabiv120__si_class_type_infoE   name@0x75993c  ti@0x759930  vt@0x759904
cls:N10__cxxabiv117__class_type_infoE
cls:N10__cxxabiv115__forced_unwindE
```

⇒ 这 3 个 vptr 就是 `__si_class_type_info` 等的 vtable 指针，签名成立。

**相比 v1 的两点放宽**（都有签名兜底，故仍属硬证据）：
1. **搜索范围**：A 区（`0x580000–0x600000`）→ **全镜像**。新增类大多在 B 区，
   例如 `CAFDataArea`(name@`0x624968`) / `CAFDataManagement`(name@`0x624db0`) /
   `CStbClientTest`(name@`0x73adf0`) / `CIQ_LensIF`(name@`0x73ed08`)。
2. **名字校验**：不再要求"长度前缀自洽"——那会漏掉**模板/嵌套**名。宽口径多出的 142 个名字
   全是真 typeinfo 名，例如：
   `9SingletonI13C3AControllerE` = `Singleton<C3AController>`、
   `14KAutoSafeArrayI14CCapBufferInfoE` = `KAutoSafeArray<CCapBufferInfo>`、
   `*N12_GLOBAL__N_121system_error_categoryE`。

### 2.2 ✘ 无效手段：Thumb 并入（对 v1 的更正）

v1 的「②Thumb 序言 +667」**并非 Thumb**。逐条核对这 667 个地址：

```
addr % 4 = {0: 667}                      ← 全部 4 字节对齐（Thumb 函数起点应为 2 字节对齐）
首 4 字节 = 0xe92d41f0 / 0xe92d4010      ← ARM  stmdb sp!,{r4-r8,lr} / {r4,lr}
```

⇒ 它们是 **Ghidra 漏识别的 ARM 函数**，与 Thumb 无关。p7 镜像里 Ghidra 的 16466 个函数
有 **16464 个是 4 字节对齐**，全镜像按 ARM 序言扫描**未发现成规模的 Thumb 代码**。
**结论：Thumb 并入收益 = 0**（真正有效的是"ARM 序言回收"，见 §3.4）。

### 2.3 ✘ 无效手段：数据引用作模块第二通道

设想：函数引用的 `DAT_xxxxxxxx` 落在某模块的 `.rodata`/`.data` 段 ⇒ 归属该模块。
**离线无该映射**：`04_strings.txt` 只给了字符串（`.rodata.str1.1`），没有各模块 `.data`
段的边界；`05_scalar_refs.txt` 给的是"常量 → 引用者"，不是"数据符号 → 所属模块"。
⇒ **收益为 0**，且做出来只能是猜测，不符合硬证据要求，故不做。
（可替代的、真正有效的是 **P 指针表**，见 §3.3。）

## 5. 仍未覆盖的部分，以及为何不可硬覆盖

- **严格口径（仅 Ghidra 函数）**：4989/16466，仍缺 **11477** 个 Ghidra 函数无硬标签。
- 根因（本轮量化）：
  1. **75.1% 的函数（12368 个）不引用任何字符串** —— 字符串是模块归属的**唯一**来源（经 `__FILE__`
     切段），无引用即无模块信号。
  2. 其中多数是无日志、非虚的**叶子/工具函数**（数学、DSP、状态机内部），既不在 vtable 里，
     也不在函数指针表里 ⇒ 离线**没有第二信号源**。
  3. `p7_callgraph.txt` 的**入度为 0 的孤立节点 433 个**（thunk/桩）本就无归属意义。
- ⇒ **60% 的硬证据已在口径 O/D 达成**；但若要求"仅统计 Ghidra 函数"的严格口径也到 60%，
  离线**不可行**（缺口 11477，且无可用信号）。这属于**不可能性结论**，不是"没找"。
