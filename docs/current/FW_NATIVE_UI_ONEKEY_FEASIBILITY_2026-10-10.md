# 「原生 UI 一键滤镜」可行性链路（★ 是否能靠重写固件达成 · 2026-10-10）

> 问题：**通过重写固件，能否实现原生 UI 一键滤镜？**
> 结论前置：**能，但"重写固件"不是那条最短的路，而且"改 p7"这个最直觉的理解是错的层次。**
> 本文把「一键滤镜」拆成三个可独立达成的子目标，逐层给出**链路 / 门槛 / 判据 / 回滚**。

---

## 0. 结论前置（三问三答）

| 问 | 答 | 依据 |
|---|---|---|
| Q1 改 **p7 固件**能做出"原生菜单里的滤镜项"吗？ | ❌ **不能，层次错了**。p7 里**根本没有 UI/菜单**（Font/DrawText/Dialog/Widget 全 0 命中，266 个 `.cpp` 无 GUI 文件）。菜单在 Linux 侧 `di-camera-app` | `CAMERA_MENU_ARCHITECTURE` §2（三条独立铁证）|
| Q2 重刷 **rootfs**（含 `di-camera-app`）能做出原生菜单项吗？ | ⚠️ **技术上能，成本极高**。SLP 无签名、可离线重打包、官方升级路径在；但 `di-camera-app` **无源码**（4.7MB Tizen app），加菜单项 = 新增 State 类 + 注册状态机 + 改 C++ 结构体数组 ⇒ 只能二进制打补丁 | `SLP_CONTAINER_FORMAT` §6 + `CAMERA_MENU_ARCHITECTURE` §3.4/§4 路 C |
| Q3 那"一键滤镜"到底要不要重写固件？ | ✅ **不要。一键今天就能做**（键钩子 + `filmlab.sh apply --fast`，已通）。重写固件只负责**补齐"效果完整度"**（全 7 维 + 成片带 LUT），不负责"一键"本身 | 本文 §3/§4 |

> ★★ **一句话**：**"一键"是交互问题（已解决，挂到原生键即可）；"滤镜完整"才是固件问题。**
> 把这两件事分开，就不需要为了"一键"去重刷固件。

## 1. 先把"原生 UI"是谁的活分清楚（否则整条链路会走错层）

| 层 | 载体 | 位置 | 我们的关系 |
|---|---|---|---|
| **ISP 渲染层** | p7 / rtos | SLP **img5** → 分区 **p7** | ★ 只画**取景器叠加层**（FD 框 / 目标框 / 过曝区）。**无菜单** |
| **系统 UI 层** | `di-camera-app`（EFL + Edje，4.7MB） | SLP **img6** → **rootfs（p10）**，**只读** | ★ **MENU 键的系统菜单就是它**。无源码 |
| **外观资源层** | `.edj` 主题（`slp_edc_menu.edj` 等 19 个） | `/usr/apps/com.samsung.di-camera-app/res/edje/`（rootfs 内） | 可解包/重编（`edje_decc`）—— **只能改观感，不能加功能** |
| **mod 层** | `/opt/usr/nx-ks/`（**p14，rw**） | **不在 SLP 的 10 段里** | ★ 我们的全部现有能力都在这里 ⇒ **刷机不会碰它** |

**p7 无 UI 的三条铁证（判据可推广）**：
1. 源码树 266 个 `.cpp`，无一 `Menu/GUI/OSD/Draw/Font/Dialog`；唯一沾显示的 `DisplayLCD.cpp` 只做 `dp_box_lcd_fd_draw`（脸框）。
2. UI 工具包必备四件套 —— `Font` / `DrawText` / `Dialog` / `Widget` —— **p7 全 0 命中**。
3. 24 个菜单核心概念（`menuIndex/submenu/CMenu/Cursor/Scroll…`）**23 个 0 命中**，唯一命中的 `selection` 是对焦区。

⇒ ★ **新铁律（已入档）**：*判某固件有没有 UI，先搜 Font / DrawText / Dialog / Widget；四件全无 ⇒ 该固件无界面，别再找菜单。*

## 2. 目标拆解：把"原生 UI 一键滤镜"拆成三个独立子目标

| 代号 | 含义 | 现状 | 靠谁说 |
|---|---|---|---|
| **G-UI** | 滤镜入口**出现在相机原生界面**（不是 mod_gui 覆盖层） | ❌ 入口是 mod_gui 覆盖层 | `di-camera-app` / Edje（rootfs）|
| **G-ONEKEY** | **一次操作**（1 次按键 / 1 次点击）即生效 | ✅ **已达成**（键钩子 + `apply --fast`）| `/opt/usr`（零固件）|
| **G-FILTER** | 滤镜**效果完整**：全 7 维 PW + 3D LUT，且**预览与成片都带** | ⚠️ 部分：预览 LUT 直灌 ✓ ｜ PW 仅三维 ｜ 成片不带 LUT ❌ | p7（ISP 侧）|

★★ **关键洞察**：用户口中的"一键滤镜"，90% 的体感来自 **G-ONEKEY**，而它**已经成立**。
"原生 UI"这个词实际混装了两件事：*"入口是原生的"*（G-UI，难）和 *"操作是一下的"*（G-ONEKEY，易）。

## 4. 三条链路详解

### 链路 A —— 零固件改写（★★ 现在就能做，推荐先做）

```
机身按键（EV+AEL / 或 S1、AEL 单键）
   └─ 已有钩子 EV_AEL.sh  ★ 改一行即可改行为（社区脚本已被替换过，通路已验证）
        └─ mod_gui 菜单（8 条配方按钮，已证可见、不卡）
             └─ 点击 = filmlab.sh apply <key> --fast
                  ├─ ① prefman 写 slot9 + save      （持久化）
                  ├─ ② setusr 切槽                  （保证"选择"发生）
                  ├─ ③ pwsend 直推                   ★ 本步=画面立即变（三维已实测 3/3）
                  └─ ④（可选）LUT1 直灌 + lutsentinel 守护   ← 预览带 LUT
```
- **达成**：G-ONEKEY ✅（1 次点击）｜G-FILTER 部分（三维 PW + 预览 LUT）
- **门槛**：无（L1，G0+G1 即绿）
- **判据**：`filmlab.sh check` = yes；取景器立即变化；`flab_sim.sh` 12/12
- **回滚**：`filmlab.sh reset`（清 slot）/ 画面向导重选「自定义1」

#### 链路 A+（更"原生"的变体 —— 1 次按键，无菜单）
```
S1 短按 → filmlab.sh cycle        （轮换下一个配方，零 UI，已证可用）
        + popup_timeout 弹当前配方名（★ 相机原生 OSD，不是我们画的）
        + prefman 记录当前项（重开机恢复）
```
- ★ **这是"最接近原生"的一键形态**：用的是**原生键 + 原生 OSD**，且完全不依赖 mod_gui。
- **上限**：内核先消费按键 ⇒ **长按/连击/组合键架构性不可得** ⇒ "一键"的天花板 = **一次按键一个动作**。
  任何"进入列表挑选"的交互**只能靠界面**。

### 链路 B —— 改 p7（重写固件，替代链路 A 的 ④ 上限）★ 需 G4

**目标：让"一键"的**效果**完整（7 维 PW + 成片 LUT），不是让入口变原生。**

```
离线（零风险，全部可复现）
 1. 扩外部 PW 归一化器：FUN_00051090
      现状  sub r3,r0,#0x100 ; cmp r3,#0x2e   ← 合法域 0x100..0x12e
      目标  cmp r3,#0x33                       ← 覆盖到 0x133（+ 跳转表 0x510b4 补 6 项
              + handler 体 0x51170-0x51390 内补 4 个 "mov r3,#0x13N / str r3,[r1]" 桩）
      ★ 难点：**等长约束** —— 段内加指令要腾地方（找现存空洞 / 等价改写 / 挪到段尾）
 2. 成片带 LUT（二选一）
      B1 让 p7 的 Still 流程**不再重配置** LUT 档位池（E4 已捕获 Cfg 0x0→0x1100 这一动作）
      B2 直接写**档位池**（Still 可达集 18 档）—— 更稳，改动更小
 3. 打包：raw8/fw/slp_pack.py patch img5 → 自动重算 JAMCRC（★ 已自证"重建 == 原件逐字节"）
刷机（★ 需 G4 双绿）
 4. SD 卡根放 nx500.bin → 机身 Settings → Device Information → Firmware Update → Body Firmware Update
```
- **达成**：G-FILTER ✅（7 维一键 + 成片 LUT）
- **门槛**：★ **G4**（G4-1 = U4 官方升级路径接受重打包 SLP；G4-2 = U5 单分区回滚演练）
- **回滚**：官方 1.13 SLP 原件在手（`.uploads/fw/nx500_v1.13.bin`）+ 11 个分区备份（`raw8/emmcbak/`）
- **副产物收益**：改 p7 还能顺手解决两个 mod 侧顽疾 ——
  **(a) 免"机身菜单手动开蓝牙"才能初始化 mod**（头号脆弱点）；**(b) 内置 LUT 表批量替换**。

### 链路 C —— 重刷 rootfs 改 `di-camera-app`（真·原生菜单项）★ 需 G4 ★★★★ 成本

```
 1. 解开 SLP img6（LZOP，280 MB）→ 得 rootfs 树
 2. 定位 /usr/apps/com.samsung.di-camera-app/{bin/,res/edje/}
 3. 加菜单项，四条子路按成本：
      C1 改 .edj 主题        → 只能改**外观**（颜色/图标/布局/字体）        ★ 低
      C2 改 .data            → 只能改**文本/数值**，**改不了行为**（行为在 .text 的 switch）★★ 中
      C3 二进制插桩新 State  → 加"新菜单项+新页面" 的唯一真路；无源码 ⇒ 需代码洞+重定位  ★★★★ 极高
      C4 复用「开发菜单」    → UI_Manage_Development_Menu_Info_By_GUI 是一条**未验证的现成入口** ★ 待查
 4. 重新 LZOP 压缩 → 回填 img6 → ★ **长度变了 ⇒ 后续所有段的 offset/len 连锁改** → 重算全部 JAMCRC
刷机：同链路 B
```
- **达成**：G-UI ✅（真·原生菜单项）
- **代价**：`di-camera-app` 菜单树深度是**编译期决定**的（每级一个 State 类）⇒ 加一级 = 加一个类 + 注册状态机 + 改 `tag_MENU_INFO`
- ★ **性价比最差**：花 10 倍成本，只买到"入口从覆盖层搬进原生菜单"这一个观感差异，且**对"一键"零增益**。

## 6. 死路与陷阱（别再撞）

| # | 陷阱 | 事实 |
|---|---|---|
| 1 | "改 p7 加菜单项" | p7 **无 UI**（四件套全 0）；层次错误 |
| 2 | "改 `.data` 把某菜单项变成滤镜" | `.data` 只存**文本/数值**，**行为在 `.text` 的 switch** ⇒ 改不动 |
| 3 | 自绘全屏 EFL UI 当"原生界面" | ★ **拖死单核**（720×480 全屏 GL 实测卡死，需物理重启）⇒ 只能小 HUD 或 mod_gui |
| 4 | 长按 / 连击 / 组合键做"多级一键" | **架构性不可得**（内核先消费）⇒ 一键的上限 = **一次按键一个动作** |
| 5 | "重刷固件会把 mod 冲掉" | ❌ `/opt/usr` = **p14，不在 SLP 10 段里** ⇒ 刷机**不碰 mod**（rootfs 本就只读） |
| 6 | "`st firmware up` 就能验 CRC" | ❌ 它内部 flag=0、**不校验 CRC** ⇒ 要验完整校验链**必须走相机 UI**（flag=1）|
| 7 | 用 `p7_patched.bin` 做实验底本 | ⛔ 那 1 字节是**复位期 DACR 写入被改成未定义编码** ⇒ 危险样本，已隔离 |
| 8 | 动 `boot0 / boot1` | ⛔ **绝不碰**（真正的第一级引导，无回滚）|
