## 〇、★★★★★ 核心纠正：`FUN_003f3fa4` 不是「Thumb veneer 桩」，是 **ARM 索引跳转表**

### 旧结论（FIRMWARE_BREAKTHROUGH §2，2026-10-07 19:20）
> 「p7 的是『ID → veneer 桩 → handler』三段式分发，不存裸函数地址。
> 这就是为什么所有『找指针 / 找 BL』的方法都零命中。」

### 本次实测：**伪代码 / 反汇编模式判断错误**

`0x3f3fa4` 处的真实指令（**ARM 模式**，不是 Thumb）：

```arm
0x3f3fa4   cmp     r1, #0x13               ; id <= 19
0x3f3fa8   ldrls   pc, [pc, r1, lsl #2]    ; ★ 索引跳转表（ARM 经典 ldrls pc）
0x3f3fac   b       #0x3f40a0               ; 默认分支: mov r0,#0 ; bx lr（返回 0）
0x3f3fb0   .word   0x803f4098              ; table[0]
0x3f3fb4   .word   0x803f4090              ; table[1]
...
0x3f3ffc   .word   0x803f4000              ; table[19]
```

**根因**：
1. 旧分析用 **Thumb 模式**解 `0x3f3fa4`，得到 `movs r3,r2; b #0x3f464c` —— 那是**误读**。
   实际是 `cmp r1,#0x13; ldrls pc,[pc,r1,lsl#2]`（ARM 4 字节指令）。
2. 表值是 **`0x803f40XX`**（高位置 1）⇒ 这是 **p7 的 MMU 虚拟地址**（VA 基址 `0x80000000`），
   不是物理地址 ⇒ 用物理地址搜索表格条目必然 0 命中。
3. `0x3f464c` 附近确实是**另一段真实 ARM 代码**（`add r7,r7,#1` 等），只是被错当成"表目标"。

### 正确结论

```
FUN_003f3fa4(struct *r0, int id):
    if (id > 0x13) return 0;
    return *(u32*)(r0 + 0x14 + id*4);      // 20 个 u32 字段访问器
```

- **表长 20**（`cmp #0x13` ⇒ id 0..19）
- **每个 handler = `ldr r0,[r0,#0x14+id*4] ; bx lr`**（单指令取值桩）
- **id 越界返回 0**

★★ **所以 p7 里"找不到函数地址表"的真正原因不是"架构上不存在"，
　而是：(a) 用错了指令集模式 (b) 表里存的是 MMU 虚拟地址。**
　⇒ 这修正了 FIRMWARE_BREAKTHROUGH §2 的"架构上不存裸地址"判据。

## 二、★★★★★ 副产品：解出 p7 的**镜头阴影（LSC）表生成器**

`FUN_003f2f64` 由上述访问器驱动，**逐像素生成一张归一化径向衰减表**，证据链完整：

### 2.1 尺寸判定（用 `FUN_003f3f74` = 字段 `+0x08`）

```c
uVar2 = FUN_003f3f74(desc);            // 读字段 +0x08
if (uVar2 < 0x801) {                   // ★ 阈值 0x801 = 2049
    iVar3    = FUN_003f3fa4(desc, 0xb);   // id 11
    local_30 = FUN_003f3fa4(desc, 0xd);   // id 13
    puVar8[0] = FUN_003f3f64(desc);       // 用描述符里的实际宽
    puVar8[1] = FUN_003f3f6c(desc);       // 用描述符里的实际高
    puVar8[2] = FUN_003f3f74(desc);
    puVar8[3] = 1;
} else {
    iVar3    = FUN_003f3fa4(desc, 6);     // id 6
    local_30 = FUN_003f3fa4(desc, 8);     // id 8
    puVar8[0] = 0x800;                    // ★ 硬编码 2048
    puVar8[1] = 0x600;                    // ★ 硬编码 1536
    puVar8[2] = FUN_003f3f74(desc);       // stride = 字段 +0x08
    puVar8[3] = 0;
}
```

★ **`0x800 × 0x600` = 2048 × 1536 = NX500 标称 28MP 全分辨的 1/1.9，
　实际就是 ISP LSC 表的固定工作分辨率（半分辨率 1:1 采样）。**

### 2.2 径向衰减公式（逐像素）

```c
uVar2 = *puVar8 >> 1;      // cx = w/2
uVar1 = puVar8[1] >> 1;    // cy = h/2
for (y = 0; y < h; y++)
  for (x = 0; x < w; x++) {
      dx = FUN_00507d70(x - cx);       // 有符号差
      dy = FUN_00507d70(y - cy);
      nx = (dx << 12) / cx;            // ★ 归一化到 Q12（±4096）
      ny = (dy << 12) / cy;
      r2 = ((nx*nx >> 12) + (ny*ny >> 12)) >> 1;   // ★ 归一化半径平方
      if (r2 > 0xffe) r2 = 0xfff;                  // 饱和
      bufA[i] = ~(u8)(r2 >> 4);        // ★ 增益表（≈ 255 - r²，越靠边越暗）
      bufB[i] = 0x7f - (u8)(r2 >> 5);  // ★ 偏置/暗电流表（≈ 127 - r²/2）
  }
FUN_003f47f8(desc, bufA,     0x1ab2600);   // ★ 输出到 p7 VA 0x1ab2600
FUN_003f47f8(desc, bufB,     0x1ab2600);   // ★ 同一目标（双通道）
```

### 2.3 关键含义

| 观察 | 含义 |
|---|---|
| 公式是**纯几何径向**（只用 dx,dy / 中心 / Q12） | ★ **p7 用软件实时算 LSC，不是查标定表** |
| 输出目标 = p7 VA `0x1ab2600` | ★ 6.3MB（2048×1536×2 表）的**专用缓冲** |
| 两张表：`~r²>>4`（增益）与 `0x7f-r²>>5`（偏置） | 对应 ISP 的 **shading gain** 与 **shading offset/black level** |
| 阈值 `0x801` 切换「用描述符尺寸」vs「固定 2048×1536」 | ★ 大图走固定尺寸（性能），小图走实际尺寸 |
| 由 `FUN_003f3104` 在 `字段+0x00 > 0x2d0 (720)` 时调用 | 只在**长焦/大图**条件下生成 |

★★ **这解释了 p7 里一个此前无法归类的大块：`0x1ab2600` 缓冲区 = LSC 表，
　由 `FUN_003f47f8`（`desc->cb` 回调）DMA 到 ISP。** 属于**走 DMA 的参数**（铁律 92 可写类）。

## 三、★★★★★ 路径 B 的寄存器接口已完整解出（★ 本次最重要的进展）

### 3.1 三个底层原语（全部 ARM，已逐条验证）

```arm
; ① 提交/触发：FUN_004ba6a8(idx)
0x4ba6a8  mov  r3, #1
0x4ba6ac  lsl  r0, r3, r0            ; bit = 1 << idx
0x4ba6b0  mov  r3, #0x1000
0x4ba6b4  movt r3, #0x2082           ; r3 = 0x20821000
0x4ba6b8  str  r0, [r3, #0x44]       ; ★ *(u32*)0x20820044 = 1 << idx
0x4ba6bc  bx   lr

; ② 槽位状态/锁：FUN_004ba5fc(idx, val)
0x4ba5fc  mov  r3, #0x1000
0x4ba600  cmp  r0, #0xf
0x4ba604  movt r3, #0x2082           ; 0x20821000
0x4ba608  ldr  r3, [r3, #0x48]       ; ★ 读 *(u32*)0x20820048
0x4ba60c  subhi r0, r0, #7           ; idx>0xf ⇒ idx -= 7
0x4ba610  lsl  r0, r0, #1            ; 每 idx 占 2 bit
0x4ba614  mov  r2, #3
0x4ba618  bic  r3, r3, r2, lsl r0    ; 清 2 bit
0x4ba61c  and  r1, r1, r2
0x4ba620  orr  r0, r3, r1, lsl r0    ; 填 2 bit
0x4ba62c  str  r0, [r3, #0x48]       ; ★ 写回 *(u32*)0x20820048
0x4ba630  bx   lr
```

| 原语 | 目标寄存器 | 语义 |
|---|---|---|
| `FUN_004ba6a8(idx)` | ★ **`0x20820044`** | **21 槽共用 1 个提交寄存器，每槽 1 bit**（`1<<idx`）|
| `FUN_004ba5fc(idx,val)` | ★ **`0x20820048`** | 每槽 **2 bit** 状态（idx>0xf 时 `idx-=7`，与低半区共享 shift）|
| `FUN_004b6fa8(class,slot,0)` | — | ★ `ldrls pc` 跳转表（**9 条目，r0<=8**）= 每 mode class 的状态机 |

★★★ **关键推论**：`0x20820044` / `0x20820048` 落在 **EP「全局控制」块 `0x20820000`**（见 FIRMWARE_BREAKTHROUGH §4），
　**不在** 参数块 A/B 的 `0x20821300/1700` 里。
　⇒ **21 槽 = 21 个参数缓冲（每槽 256B @0x20821300/1700）+ 1 个共享提交位图 + 每槽 2bit 状态。**

### 3.2 槽位分配器：`FUN_0013c498` —— **8 个描述符槽，stride 0xc9**

```c
void FUN_0013c498(int p) {                   // p = 上下文基址
  *(u8*)(p+0xc9)  = 0xff;   // slot[0].idx = 0xff（未分配）
  *(u8*)(p+0x191) = 0xff;   // slot[1]   (0x191 = 0xc9 + 0xc8)
  *(u8*)(p+0x259) = 0xff;   // slot[2]
  *(u8*)(p+0x310) = 0xff;   // slot[3]
  *(u8*)(p+0x3c8) = 0xff;   // slot[4]
  *(u8*)(p+0x480) = 0xff;   // slot[5]
  *(u8*)(p+0x538) = 0xff;   // slot[6]
  *(u8*)(p+0x5f0) = 0xff;   // slot[7]
  memset(p+8,    0, 0xb0);  // slot[0].buf[176B]
  memset(p+0xd0, 0, 0xb0);  // slot[1]  ... ×8
  *(u32*)(p+0x5f8) = 1;
  *(u32*)(p+0x600) = 1000;  // ★ 1000 = 可能是超时/计数上限
}
```

**槽结构（stride `0xc9` = 201B）**：`+0x08..+0xb7` = 176B 参数缓冲；
　`+0x10` = 双缓冲选择（`FUN_004b6894` 的 `param_3`）；`+0x11/0x12/0x13` = `thunk_FUN_004ba6a8` 的提交索引。

### 3.3 调用者矩阵（29 个）—— 只有 3 个槽是**静态硬编码**的

| 槽号 | 使用形态 | 说明 |
|---|---|---|
| **0, 1, 2** | 字面量（`FUN_004b6894(0,…)` / `(1,…)` / `(2,…)`） | ★ **仅 3 个槽被静态引用** |
| 其余 | `*(char*)(ctx+5)` / `+7` / `+8` | ★ **运行期动态分配**（由 `FUN_0013c498`/`FUN_0013c5d4` 决定）|

★ **`FUN_0013c5d4(mode)` 返回分配到的槽号**：`mode==1 → FUN_004b6fa8(6,2,0)` ⇒ 槽 **2**；
　`mode==2 → FUN_004b6fa8(7,3,0)` ⇒ 槽 **3**。⇒ **槽↔功能 映射由运行期 mode 决定，不写死在镜像里。**

★★★ **这解释了「为什么静态看不到槽语义」**：槽是**池化 + 动态分配**的。
　⇒ **路径 B 判据实验（只读）现在有了明确对照目标：
　　同时读 `0x20820044`（提交位图）与 `0x20820048`（槽状态），可看到槽的「活动位」。**

### 3.4 与 LSC 通路的汇合（★ 关键证据）

`FUN_003f773c`（LSC 表生成器）**直接调用参数块写入器**：

```c
iVar5 = FUN_004b6894((int)cVar1, puVar3, *(u8*)(iVar4+0x10));   // ← 参数块 A @0x20821300
thunk_FUN_004ba6a8(*(u8*)(iVar4+0x12));                          //   ★ 提交（1<<idx）
iVar5 = FUN_004b6b98((int)*(char*)(iVar4+6), local_1ac, *(u8*)(iVar4+0x10));  // ← 参数块 B @0x20821700
thunk_FUN_004ba6a8(*(u8*)(iVar4+0x13));                          //   ★ 提交（1<<idx）
```

⇒ ★★★★★ **LSC 表 与 ISP 参数块 A/B 是【同一条通路】的不同层** —— 都经 `FUN_004b6894/6b98`
　写槽 + `FUN_004ba6a8` 提交。这**证实了路径 B 的机制真实存在且可被 p7 自身驱动**。

## 四、★★★★ 与魔灯路线的关系

| 项 | 影响 |
|---|---|
| 色彩通路 | ★ **无直接冲突** —— LSC 是**亮度/几何**校正，不是色彩映射 |
| 但同属 ISP | ★ **间接机会**：LSC 表走 DMA 到 ISP，与 3D LUT 是同一条 DMA 机制 ⇒ 证实"走 DMA 的可注入"判断 |
| 描述符回调 `+0x7c` | ★★★ **新注入点候选**：若能在 p7 描述符里替换 `+0x7c` 回调，可劫持所有 DSP 表输出 |
| ★★ 提交寄存器 `0x20820044` | ★★★★ **路径 B 的直接落点**：21 槽每槽 1 bit，Linux 侧可直写（EP 寄存器）|

### 4.2 对「路径 B」（ISP 参数块 0x20821300/1700）的意义

★ **本文没有推翻路径 B，反而给出了完整机制**：p7 是【软件生成 → 写槽 → 提交位图 → DMA 下发】。
⇒ 路径 B 的 21 槽 = 该机制的**参数缓冲**，`0x20820044` = 提交闸门。
⇒ ★ 但**「写进去」≠「被消费」**（铁律 92/判据纪律）：槽是否被 p7 主循环消费，仍需 `iqr` 对照。

★ **路径 B 的判据实验（上机只读）—— 更新后的顺序**：
```
① 上机跑 iqr，dump 全部 184 个 eIQ_ID_* 的当前值            （只读）
② epmc.arm 读 0x20821300/1700 两块 21×10 寄存器             （只读，≤768 regs）
③ ★ 新增：读 0x20820044（提交位图）与 0x20820048（槽状态）  （只读，2 个 reg）
④ PC 侧关联：iqr 的哪些 ID = 哪些槽；活动位图哪几位亮       （本地比对）
⑤ 判据成立 ⇒ 路径 B 可解；不成立 ⇒ 退回路径 A（3D LUT）
```

### 4.3 方法论增量（已升格为铁律 113/114/115）

> ★★★★★ **铁律 113：判「跳转表分发」前必须先确定指令集模式（ARM/Thumb）。**
> 混编镜像里同一段字节用错模式解码会得到**看似合理但完全错误**的分发表
> （本案例：把 ARM `cmp+ldrls pc` 误读成 Thumb `movs+b`，凭空造出 7 条"veneer"）。
>
> ★★★★ **铁律 114：表条目若是高位置 1 的地址（`0x8xxxxxxx`），先怀疑是 MMU 虚拟地址。**
> p7 VA 基址 = `0x80000000`（文件偏移 = VA − 0x80000000）。
>
> ★★★★ **铁律 115：p7 的 ISP 参数下发范式 = 软件算好 → 写槽 → 提交位图 → DMA**
> （非"用户直写寄存器即生效"）；但 `0x20820044` 提交位图本身是 EP 寄存器，Linux 侧可达。

## 六、★ 一句话结论

> **纠正：`FUN_003f3fa4` 是 ARM「20 字段访问器」（`ldrls pc,[pc,r1,lsl#2]` 跳转表），
> 不是 Thumb veneer 桩 —— 之前是 ARM/Thumb 混编导致的解码错误。**

> **副产品 1：解出 p7 的镜头阴影（LSC）表生成器 `FUN_003f2f64`，
> 它纯几何实时计算 2048×1536 的增益/偏置双表，经 `desc->cb` DMA 到 ISP（缓冲 p7 VA `0x1ab2600`）。**
>
> ★★ **副产品 2（最重要）：路径 B 的寄存器接口已完整解出 ——**
> **21 槽参数缓冲（`0x20821300/1700`）+ 共享提交位图 `0x20820044`（每槽 1 bit）+ 每槽 2bit 状态 `0x20820048`；
> 槽由 `FUN_0013c498` 池化分配（8 槽 × stride 0xc9），只有 3 个槽被静态引用，其余运行期绑定。**
>
> ★ **对魔灯的意义：色彩通路无冲突；`0x20820044` 提交位图是 Linux 侧可直写的 EP 寄存器
> ⇒ 路径 B 有了明确落点。但「写进去」≠「被消费」，仍须 `iqr` 对照判据（上机只读，零风险）。**
