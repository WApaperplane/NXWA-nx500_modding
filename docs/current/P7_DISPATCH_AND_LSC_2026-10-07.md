## 〇、★★★★★ 核心纠正：`FUN_003f3fa4` 不是「Thumb veneer 桩」，是 **ARM 索引跳转表**

### 旧结论（FIRMWARE_BREAKTHROUGH §2，2026-10-07 19:20）
> 「p7 的是『ID → veneer 桩 → handler』三段式分发，不存裸函数地址。
> 这就是为什么所有『找指针 / 找 BL』的方法都零命中。」

### 本次实测：**伪代码 / 反汇编模式判断错误**

`0x3f3fa4` 处的真实指令（**ARM 模式**，不是 Thumb）：

```arm
0x3f3fa4   cmp     r1, #0x13               ; id <= 19
0x3f3fa8   ldrls   pc, [pc, r1, lsl #2]    ; ★ 索引跳转表（ARM 经典 ldrls pc）
0x3f3fac   b       #0x3f40a0               ; 默认分支: mov r0,#0 ; bx lr（返回 0）
0x3f3fb0   .word   0x803f4098              ; table[0]
0x3f3fb4   .word   0x803f4090              ; table[1]
...
0x3f3ffc   .word   0x803f4000              ; table[19]
```

**根因**：
1. 旧分析用 **Thumb 模式**解 `0x3f3fa4`，得到 `movs r3,r2; b #0x3f464c` —— 那是**误读**。
   实际是 `cmp r1,#0x13; ldrls pc,[pc,r1,lsl#2]`（ARM 4 字节指令）。
2. 表值是 **`0x803f40XX`**（高位置 1）⇒ 这是 **p7 的 MMU 虚拟地址**（VA 基址 `0x80000000`），
   不是物理地址 ⇒ 用物理地址搜索表格条目必然 0 命中。
3. `0x3f464c` 附近确实是**另一段真实 ARM 代码**（`add r7,r7,#1` 等），只是被错当成"表目标"。

### 正确结论

```
FUN_003f3fa4(struct *r0, int id):
    if (id > 0x13) return 0;
    return *(u32*)(r0 + 0x14 + id*4);      // 20 个 u32 字段访问器
```

- **表长 20**（`cmp #0x13` ⇒ id 0..19）
- **每个 handler = `ldr r0,[r0,#0x14+id*4] ; bx lr`**（单指令取值桩）
- **id 越界返回 0**

★★ **所以 p7 里"找不到函数地址表"的真正原因不是"架构上不存在"，
　而是：(a) 用错了指令集模式 (b) 表里存的是 MMU 虚拟地址。**
　⇒ 这修正了 FIRMWARE_BREAKTHROUGH §2 的"架构上不存裸地址"判据。

## 一、★★★★★ 由跳转表解出的完整描述符结构

以 `FUN_003f3fa4` 为中心的**同族访问器**（全部 `ldr r0,[r0,#off] ; bx lr`）：

| 访问器 | 读偏移 | 语义（由调用点推断） |
|---|---|---|
| `FUN_003f3f64` | `+0x00` | 字段 0 |
| `FUN_003f3f6c` | `+0x04` | 字段 1 |
| `FUN_003f3f74` | `+0x08` | ★ **宽度/尺寸**（见 §2，`< 0x801` 阈值） |
| `FUN_003f3f7c` | `+0x0c` | 字段 3 |
| `FUN_003f3f84` | `+0x10` | 字段 4 |
| **`FUN_003f3fa4`** | **`+0x14..+0x60`** | ★★ **20 个 u32 字段**（id 0..19） |
| `FUN_003f3f8c` | `+0x68` | 字段（与 `+0x6c` 成对） |
| `FUN_003f3f94` | `+0x6c` | 字段（≈ 宽高对） |
| `FUN_003f3f9c` | `+0x70` | 字段 |
| `FUN_003f4158` | `+0x64` | **byte 标志位**（`ldrb`） |
| `FUN_003f47f8` | `+0x7c` | ★ **函数指针回调**（`blx r3`） |

**写侧**（memcpy 风格，确认字段布局）：

| 函数 | 行为 |
|---|---|
| `FUN_003f3f38(dst,src)` | 复制 4 words from `src+0x00` |
| `FUN_003f40a8(dst,src)` | 复制 4 words from `src+0x14`（字段 0..3）|
| `FUN_003f40d4(dst,src)` | 复制 4 words from `src+0x28`（字段 5..8）|
| `FUN_003f3d5c` | 写 5 words at `+0x3c` |
| `FUN_003f3eb4` | 写 5 words（通用备份/恢复）|
| `FUN_003f3ee4` | 写 5 words at `+0x68` |
| `FUN_003f3904` | 清零 `+0x7c` |
| `FUN_003f418c` | 读 `+0x14,18,1c,20,24,28,2c`（7 个）+ 从 `+0x30` 复制 |
| `FUN_003f423c` | 读 `+0x28,2c,30,34,38,3c,40`（7 个）+ 从 `+0x44` 复制 |

⇒ ★★★ **描述符布局（推定）**：
```
struct P7Desc {
  u32 f[5];              // +0x00 .. +0x10   （f[2] 疑似宽度）
  u32 g[20];             // +0x14 .. +0x60   ★ 主参数组（跳转表 id 0..19）
  u8  flag;              // +0x64
  u32 h, i;              // +0x68, +0x6c     （≈ 宽/高 对）
  u32 j;                 // +0x70
  u32 cb;                // +0x7c  ★ 回调函数指针
};
```

## 二、★★★★★ 副产品：解出 p7 的**镜头阴影（LSC）表生成器**

`FUN_003f2f64` 由上述访问器驱动，**逐像素生成一张归一化径向衰减表**，证据链完整：

### 2.1 尺寸判定（用 `FUN_003f3f74` = 字段 `+0x08`）

```c
uVar2 = FUN_003f3f74(desc);            // 读字段 +0x08
if (uVar2 < 0x801) {                   // ★ 阈值 0x801 = 2049
    iVar3    = FUN_003f3fa4(desc, 0xb);   // id 11
    local_30 = FUN_003f3fa4(desc, 0xd);   // id 13
    puVar8[0] = FUN_003f3f64(desc);       // 用描述符里的实际宽
    puVar8[1] = FUN_003f3f6c(desc);       // 用描述符里的实际高
    puVar8[2] = FUN_003f3f74(desc);
    puVar8[3] = 1;
} else {
    iVar3    = FUN_003f3fa4(desc, 6);     // id 6
    local_30 = FUN_003f3fa4(desc, 8);     // id 8
    puVar8[0] = 0x800;                    // ★ 硬编码 2048
    puVar8[1] = 0x600;                    // ★ 硬编码 1536
    puVar8[2] = FUN_003f3f74(desc);       // stride = 字段 +0x08
    puVar8[3] = 0;
}
```

★ **`0x800 × 0x600` = 2048 × 1536 = NX500 标称 28MP 全分辨的 1/1.9，
　实际就是 ISP LSC 表的固定工作分辨率（半分辨率 1:1 采样）。**

### 2.2 径向衰减公式（逐像素）

```c
uVar2 = *puVar8 >> 1;      // cx = w/2
uVar1 = puVar8[1] >> 1;    // cy = h/2
for (y = 0; y < h; y++)
  for (x = 0; x < w; x++) {
      dx = FUN_00507d70(x - cx);       // 有符号差
      dy = FUN_00507d70(y - cy);
      nx = (dx << 12) / cx;            // ★ 归一化到 Q12（±4096）
      ny = (dy << 12) / cy;
      r2 = ((nx*nx >> 12) + (ny*ny >> 12)) >> 1;   // ★ 归一化半径平方
      if (r2 > 0xffe) r2 = 0xfff;                  // 饱和
      bufA[i] = ~(u8)(r2 >> 4);        // ★ 增益表（≈ 255 - r²，越靠边越暗）
      bufB[i] = 0x7f - (u8)(r2 >> 5);  // ★ 偏置/暗电流表（≈ 127 - r²/2）
  }
FUN_003f47f8(desc, bufA,     0x1ab2600);   // ★ 输出到 p7 VA 0x1ab2600
FUN_003f47f8(desc, bufB,     0x1ab2600);   // ★ 同一目标（双通道）
```

### 2.3 关键含义

| 观察 | 含义 |
|---|---|
| 公式是**纯几何径向**（只用 dx,dy / 中心 / Q12） | ★ **p7 用软件实时算 LSC，不是查标定表** |
| 输出目标 = p7 VA `0x1ab2600` | ★ 6.3MB（2048×1536×2 表）的**专用缓冲** |
| 两张表：`~r²>>4`（增益）与 `0x7f-r²>>5`（偏置） | 对应 ISP 的 **shading gain** 与 **shading offset/black level** |
| 阈值 `0x801` 切换「用描述符尺寸」vs「固定 2048×1536」 | ★ 大图走固定尺寸（性能），小图走实际尺寸 |
| 由 `FUN_003f3104` 在 `字段+0x00 > 0x2d0 (720)` 时调用 | 只在**长焦/大图**条件下生成 |

★★ **这解释了 p7 里一个此前无法归类的大块：`0x1ab2600` 缓冲区 = LSC 表，
　由 `FUN_003f47f8`（`desc->cb` 回调）DMA 到 ISP。** 属于**走 DMA 的参数**（铁律 92 可写类）。

## 三、★★★★ 与魔灯路线的关系

### 3.1 对本项目主线（3D LUT / 色彩）的影响

| 项 | 影响 |
|---|---|
| 色彩通路 | ★ **无直接冲突** —— LSC 是**亮度/几何**校正，不是色彩映射 |
| 但同属 ISP | ★ **间接机会**：LSC 表走 DMA 到 ISP，与 3D LUT 是同一条 DMA 机制 ⇒ 证实"走 DMA 的可注入"判断 |
| 描述符回调 `+0x7c` | ★★★ **新注入点候选**：若能在 p7 描述符里替换 `+0x7c` 回调，可劫持所有 DSP 表输出 |

### 3.2 对「路径 B」（ISP 参数块 0x20821300/1700）的意义

★ **本文没有推翻路径 B，但给出了新证据：p7 有【软件生成 → DMA 下发】的完整模式。**
⇒ 路径 B 的 21 槽很可能是**同类"p7 算好 → EP 寄存器/描述符"**的结构，
　而不是"用户直接写 EP 就能生效"。

★ **路径 B 的判据实验（上机只读）不变**，但**新增一条观察项**：
```
④ 若上机能读 p7 VA 0x1ab2600 附近（看 LSC 表是否真在那）——作为 p7 内存布局的额外锚点
   （注：Linux 读 p7 内存通道已全部排除，见 HANDOVER §2.3 ⇒ 此项大概只能由 p7 自身日志验证）
```

### 3.3 方法论增量（新增铁律候选）

> ★★★ **铁律 113（候选）：判"跳转表分发"前必须先确定指令集模式（ARM/Thumb）。**
> 混编镜像（p7 = ARM+Thumb）里，同一段字节用错模式解码会得到**看似合理但完全错误**的分发表
> （本案例：把 ARM `cmp+ldrls pc` 误读成 Thumb `movs+b`，凭空造出 7 条"veneer"）。

> ★★★ **铁律 114（候选）：表条目若是高位置 1 的地址（如 `0x8xxxxxxx`），先怀疑是 MMU 虚拟地址，不是物理地址。**
> 用物理地址搜索会 0 命中，从而误判"表不存在"。

## 五、★ 一句话结论

> **纠正：`FUN_003f3fa4` 是 ARM「20 字段访问器」（`ldrls pc,[pc,r1,lsl#2]` 跳转表），
> 不是 Thumb veneer 桩 —— 之前是 ARM/Thumb 混编导致的解码错误。**
>
> **副产品：解出 p7 的镜头阴影（LSC）表生成器 `FUN_003f2f64`，
> 它纯几何实时计算 2048×1536 的增益/偏置双表，经 `desc->cb` DMA 到 ISP（缓冲 p7 VA `0x1ab2600`）。**
>
> ★ **对魔灯的意义：色彩通路无冲突；但证实了 p7「算好→DMA→ISP」的注入范式，
> 且 `desc+0x7c` 回调是一个新的潜在劫持点。路径 B 判据实验照常，新增 p7 内存锚点观察项。**
