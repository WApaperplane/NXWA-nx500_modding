## 0. 结论

1. **V5 静态部分已完成**：归一化器扩表仍采用候选 A（file offset `0x11504`），候选 B/C 只作回退。静态包装 ELF 把整个 P7 payload 映射为 RWE，不能据此证明真实运行时段权限或空洞不会被覆盖；最终判据仍是 A1 Step1 刷后回读和零区存活探针。
2. **V6 拆成两问**：
   - **V6a，P7 内部槽变化是否触发 PW 应用：已确认。** `FUN_80053330` 的 `0xda..0xe2` 分支调用 `FUN_80051ab8`。
   - **V6b，Linux/App 是否已有外部入口可直达该通知器：仍未知。** REA 只枚举出三个静态直接调用者，且明确不表示无目标地址的间接/计算流；不能把“未看到”写成“不存在”。
3. **当前不新增“外部→档位池”补丁方案**。先按既定顺序完成 A1 Step1/full 和 C-2 上机判据。若以后追 V6b，目标应是运行时注册表/回调来源，而不是重做 `di-camera-app` 全量静态分析。

## 3. V6：REA 证据

### 3.1 函数入口

REA 在正确 VA `0x80053330` 解码到：

```text
bytes: 10 40 2d e9
instruction: stmdb sp!,{r4,lr}
procedure: 0x80053330
status: decoded
```

证据 ID：`ev_4c6a4cbfd74da216fcdc64eca9aa5371aab921b3e3f7e997f501447cc0198a11`。

### 3.2 函数档案

REA 将入口识别为 `FUN_80053330`。由于大型跳转表，Ghidra 给出的函数体是非连续地址集（8932 B，跨度 12288 B）；这能辅助建立引用图，但精确 switch 语义仍应与手工/Capstone 解码互证。

静态直接调用者：

| 调用者 | 备注 |
|---:|---|
| `0x8004cd74` | 已有手工分析中的短包装器 |
| `0x80056330` | Ghidra 函数体非连续 |
| `0x80056898` | Ghidra 函数体非连续 |

关键伪代码：

```c
case 0xda:
case 0xdb:
case 0xdc:
case 0xdd:
case 0xde:
case 0xdf:
case 0xe0:
case 0xe1:
case 0xe2:
    FUN_80051ab8();
    break;
```

这与既有手工结论“PW 9 个槽发生变化时调用档位应用函数”一致。函数档案证据 ID：`ev_f298211bd8f7a6a1f8f29327cfaee8a0b3f6e71322e1ae282587f40254672acf`。

### 3.3 证据边界

REA 对该档案明确声明：无目标地址的未解析计算流或间接流不会成为引用边。因此目前只能得到：

- **确认** `FUN_80053330 → FUN_80051ab8` 的内部触发关系；
- **确认**上述三个静态直接调用者；
- **不能确认**是否存在运行时表注册、函数指针或消息分发间接到达 `FUN_80053330`；
- **不能因静态图中没有 App/Linux 调用者，就断言外部入口不存在**。

## 4. 对“魔灯式、但使用原生 UI”的设计影响

建议维持三层，而不是把所有能力塞进一个外挂菜单：

| 层 | 职责 | 当前实现/下一步 |
|---|---|---|
| 原生交互层（`di-camera-app`） | 页面、滚轮、焦点、文本、状态同步 | 复用官方“画面向导/自定义槽”控件与状态机；C-2 是受控桥接和验证入口，不把 shell 菜单当最终 UI |
| 能力层（P7） | 参数归一化、PW 7 维和应用触发 | A1 只扩展既有归一化器，保留原厂越界拒收和回滚路径 |
| 数据层（p14） | 配方、LUT、标签和版本化配置 | 保持数据可更新、代码补丁最小；由 App 原生页面选择，由 P7/现有工具执行 |

落地顺序：

1. **先证明能力层安全**：A1 Step1 → 稳定观察 → A1 full。
2. **再证明 App 桥接可靠**：C-2 通过 T2 bind-mount 上机，验证启动、休眠/唤醒、重启和回滚。
3. **再做原生 UI 产品化**：优先改现有画面向导页面的数据源、标签和 handler 映射；不要另画悬浮层，也不要在 P7 里造菜单。
4. **最后才扩展入口数量**：先接受官方 3 个自定义槽的 UI 天花板；只有在页面模型/Edje part/焦点链都可复现后，才评估增加列表项，避免把“小补丁”升级成状态机重写。

这一路线和魔灯的目标相似——能力可扩展、可回滚、版本化——但呈现层仍是三星原生 UI，插件边界放在数据与命令 ABI，而不是另起一套覆盖层。
