## 0. 结论

1. **同意转向：poker（运行时内存注入）退出 UI 修改的投递主候选序列** ⇒ 降级为「参数级口袋工具」（既有比特率功能保持不动）。
   - 关键理由：UI 路线的核心交付（M2/M3/M4）需要**新逻辑执行/新接线**，poker 只能**写数据值**——能力错配；且与离线补丁族（C-2 / T1 / T2）相比，在可验证性、可控性上全线劣后（§2.3）。
2. **澄清一（不为否定而否定）**：poker 不是死路——它是参数级（比特率式）的**成熟工具**，保留使用；本轮降级的是它作为「UI 投递通道」的候选地位，不是工具本身。
3. **澄清二（转向的落点要修正）**：「转向固件级 / app 级」的第一站**不是**写 UI 补丁，而是**修复 app 级投递链的两个 10-13 实测缺口**（§3）——C-2 上机在没有干净生效语义之前，验不出有效结论。

## 1. poker 能力盘点（已证 / 未证）

### 1.1 已证（先例 = 9 组比特率内存补丁）

| # | 项 | 证据 |
|---|---|---|
| 1 | 写「预编码值」到运行中 App 的**固定数据地址** | `a_init.sh` 对 `0xb4095a08` 等 9 个地址写 `c0f68910` 等编码值（= `pokemon` 表中比特率编码）；`pokemon` 逐值可对照 |
| 2 | 写入**被消费** | 比特率功能为 mod 既有功能（`Pro4K=160 …` 经 `br_up.sh`→`a_init.sh` 生效） |
| 3 | 工具链完整 | `poker`（写入器）+ `pokemonche`（编码查表）+ `pokemon`（交互式）+ `init_auto.tp`/`br_up.sh`（每开机渲染 `a_init.sh`） |
| 4 | 写入无障碍 | App 非 PIE（EXEC）、无签名闸门、root 运行；`pgrep di-camera-app` 取 PID 后直接写 |
| 5 | 注入点时序 | `a_init.sh` 由开机 mod 链（bluetoothd→init.sh 之后）触发——**晚于 App 启动（boot+12.2s）约 25s 以上**——晚注入+事后重读是该通道的既有工作模式 |

### 1.2 未证（UI 需要、但零先例）

| # | 缺口 | 含义 | 验证法 |
|---|---|---|---|
| G1 | **文本/表数据的生命周期与刷新时机** | 菜单字符串何时读入、写内存后 UI 如何/是否会重读——**0 证据** | 需 RE（文本引用链）+ 上机探 |
| G2 | **指令级写入（trampoline）** | icache 刷新 / 多字节原子性 / 线程执行位置 / 代码区权限——四条件全未证；poker 是否做 cache flush 未知 | 二进制分析 poker + 专项上机（高风险） |
| G3 | **新目标地址定位** | 9 个比特率地址是当年逆向成果；换目标（如菜单数据）= 新的 RE 工作量 | RE 分析（与「直接做离线补丁」同源，无捷径） |
| G4 | **不能加载 .so / 不能注入新逻辑** | poker 只能改既有内存，不能执行新代码 | 工具性质决定，不可绕过 |

### 1.3 小结

poker 的证明面 = 「固定地址 × 预编码数据 × 事后重读的参数」；UI 的需求面 = 「新交互逻辑 × 新代码执行 × 文本/表管理」。**交集 ≈ 空集边缘**（仅 §2.2 一格）。

## 2. 用途匹配与横向对比

### 2.1 与 UI 路线交付的逐项对照

| UI 交付（NATIVE_UI_ROADMAP） | 需要什么 | poker 能否承担 |
|---|---|---|
| M1 原生入口（菜单出现） | 菜单新增条目/接线（改表结构/代码） | ❌ |
| M1′ 替换既有文本（UI-R2b/R3b 最小实验） | 写文本数据 | ⚠️ **唯一沾边**——但受 G1（生命周期/时机）未证约束；且即使成功只是显示层 |
| M2 三槽映射交互 | 新选中/映射/状态逻辑 | ❌ |
| M3 一键应用 | 执行新代码（触发事务/脚本） | ❌（不能注入逻辑） |
| M4 配方浏览 | 新页面/列表逻辑 | ❌ |

### 2.2 ★ 与离线补丁族同项对比（同目的、不同工具）

> 「离线补丁族」= C-2 补丁体 + 投递（T1 rootfs 就地 / T2 bind-mount）。NATIVE_UI_ROADMAP §5 候选 C 即此族。

| 维度 | poker 运行时注入 | 离线补丁族（C-2/T1/T2） |
|---|---|---|
| 能力上限 | 数据值 / 固定字段 | 任意深度（=改代码） |
| 生效语义 | 依赖「写时机 vs 读时机」巧合；注入点晚于 App 25s+ | 取决于投递动作（§3 有缺口，但可控可设计） |
| 可验证性 | 写后无痕；无法 diff；无离线等价物 | **QEMU 13/13 全绿** + 可逐字节比对 + bytepatch 明文 |
| 可回滚 | 重启即原（看似优点） | umount / 逆写 / 重刷；证据链完整 |
| 风险面 | **运行时扰动**——本机对 App 生命周期极敏感（restart 卡死 / hibernation 联锁；见 CAMERA_ONLINE_PROBE §2/附 C） | 静态错误离线可拦（QEMU/比对） |
| 现状 | 参数级成熟；UI 级零实践 | 补丁体+T2 件+QEMU 全绿 = **只差上机** |
| 增量投入 | 要解 G1/G2/G3 三题（RE + 高风险实验） | 已投入完成；剩「生效路径」修复（§3） |

**⇒ 结论**：同一目的下，离线补丁族在能力、可控性、风险三项全面占优；poker 的独有优势（「不部署、当场生效」）在 UI 场景**不兑现**——恰恰因为 UI 数据在 App 启动期已加载（G1），poker 的「晚注入」反而成为短板。

### 2.3 对 HANDOVER §4.2-3 原建议的修正

原建议「先试 poker、不必先动 UI 源码」的价值被高估，原因：
1. 它假设了 poker 与 UI 需求的能力匹配，而实际交集仅在「文本替换」一格；
2. 「文本替换」这一格恰恰是 poker 短板（生命周期/时机），却是离线补丁的长板（改文件字节，加载时机确定）；
3. 「不必先动 UI 源码」的替代并不需要 poker——T1/T2 同样「不动 UI 源码」（不动逻辑，只动字节/挂载）。

## 3. ★ 两个必须正视的投递缺口（本轮文献交叉核对发现，尚未复评）

> 以下两点是 **10-13 晚实测**对 **10-12 设计**的推翻；`dicam_patch_install.sh`（10-12 落款）与 `TASKFLOW_2026-10-12` W-3 尚未吸收，属于**悬空设计缺口**——转向 app 级时第一批要修的就是它们。

### 3.1 缺口 A：「本块必须早于 di-camera-app.service」已被推翻

- 10-12 设计依据：init.sh（bluetoothd 钩子）早于 `di-camera-app.service` ⇒ bind-mount 赶得上 App exec；
- **10-13 实测**：App = boot+12.2s，init.sh = boot+37.8s ⇒ **mount 永远晚 25s**（CAMERA_ONLINE_PROBE §1-2）；
- 含义：**冷启动时 mount 赶不上本次 App exec**；「正常关开机生效」的语义需要论证——或者找到「晚于 mount 的 App exec 时刻」（是否存在=待实测），或者把挂载前移（§3.3）。

### 3.2 缺口 B：「立即生效」依赖的 `systemctl restart` 已证死

- `dicam_patch_install.sh` 第 4 步「立即生效」= `bind-mount + systemctl restart di-camera-app`；
- **10-13 实测**：restart 该 unit ⇒ **整机卡死（须物理重启）**——该步骤作废；
- 同样受影响：`TASKFLOW W-3` E-D4 演练（「restart 后画面正常 ⇒ 机制可用」判据）、DICAM_MOD_DESIGN 中「restart 后画面正常」类判据、DICAM_PATCH_INSTALL_PATHS §5 失败模式里的 restart 建议；
- ⇒ **全部改为「删挂载/回滚 → 自然关机开机」路径**（与 NATIVE_UI_ROADMAP §2 的口径对齐）。

### 3.3 候选解法（三选一或组合，需专项裁决）

| 解法 | 内容 | 代价 / 风险 |
|---|---|---|
| a) P5 式前置挂载 | 改 `di-camera-app.service` **unit 本体**加 `ExecStartPre=` 挂载脚本（rootfs 写入；与既有 bluetoothd wrapper 同类先例） | rootfs 改动需并入「刷机后自动重装链」（install.sh 目前不碰 unit） |
| b) T1 就地补丁（回退选项） | 直接改 rootfs 里的 App 字节（**无时序问题**：exec 时加载的就是改后文件） | 刷机后被官方 rootfs 覆盖 ⇒ 接受「刷机后重放」（D-5 预案原文即此） |
| c) 生命周期实测 | C-2 上机先探「是否存在晚于 mount（boot+38s 后）的 App 重启/重 exec 时刻」 | 依赖实测；若存在则 T2 原方案成立 |

> ★ 这三条正是 REA_P7_V5_V6 把「C-2 上机」列为「验证 T2 投递生命周期」的执行内容——**先解它，再写 UI 补丁面**。
