## 2. 补丁化空间的层次模型

```
L0 零补丁（脚本/工具接线）   ← ★ 最被低估的一层
L1 App 数据表补丁（改名复用命令槽）      ← C-2 已证
L2 App 代码补丁（改/加 handler 逻辑）
L3 p7 补丁（数据/逻辑）                 ← ★ 真正的金矿
L4 其它固件（libudd5 / Edje 主题 / 其它 app）
L5 内核 / boot0-1 / SLP 头              ← ⛔ 禁区
```

**层级越深，收益上限越高，但"能不能退回来"越难。** 判据见 §7。

## 3. ★ L0：零补丁，但从未接线（最被低估）

> ★★ **2026-10-12 W-6 实测补充**（详见 `W6_CAPABILITY_PROBE_2026-10-12.md`）：
> `st cap` **实有 23 条命令，mod 只用了 6 条**（`capdtm`/`capt`/`iq`/`iqr`/`lens`/`sh`）。
> 本次探出 5 条高价值零补丁通道：
>
> | 通道 | 内容 | 对项目的意义 |
> |---|---|---|
> | **`st cap ref`** | **p7 的 T-Kernel 调试通道**：`ref stack`（任务表+**栈地址**）/ `ref int`（中断计数）/ `ref mem|tsk|reg`（待探） | ★★ `ref stack` 显示所有任务栈在 `0x81823xxx`~`0x821a5xxx`，**远离 A1 特判块 `0x80011504`** ⇒ 排除"零区被栈覆盖"（旁证） |
> | **`st cap path dump ep`** | EP 寄存器 dump（`0x20821000/0x20823000/0x20826000` 三块） | ★★ 正是 `/dev/mem` **读不到**的那片区（G2b）⇒ 死路 #6 补全为"走驱动**或**走 cap 通道" |
> | **`st cap lockinfo`** | 实时曝光（Av/Tv/Iso/DeltaEv）+ 场景识别 + AF 结果 | ★★ 脚本可读相机内部状态 |
> | **`st cap seq`** | 拍摄 sequencer 调试（`status`/`log`/`order`/`check`/`wbtest`） | ★ 流程级调试 |
> | `st cap back` | 厂测（`uniteset`/`matr`） | 低 |
>
> ⛔ 空实现（0 字节）：`obj` `al` `str` `path info`｜❓ 未探（风险不明）：`sh` / `sh-ad`（疑为 shell 执行）。
> **⇒ 判据 J1（零补丁穷尽）得到强力印证：这一层比预想厚得多。**

## 4. L1–L2：App 层补丁空间（C-2 已开的路子）

### 4.1 命令槽池（可复用的"遗体"）

顶层命令表 32 条中，**厂测/低频**者可作为新功能宿主：

`test`（厂测，子命令极多）｜`rr` ｜`uscap` ｜`usetc` ｜`strobe` ｜`softap`（重复项）｜`ap` ｜`flip` ｜`gengrid data`

- C-2 只用了 `uscom` 一个（135 B 遗体）
- 每个宿主可承载 **~200–600 B** 的桩代码（遗体长度决定）

### 4.2 但边际收益在递减 —— 为什么

**App 能做的动作，命令表里基本都有；补丁加不出"App 本来不会做的事"。**
C-2 的真正价值是**"开了 mod ↔ App 的双向通道"**（可脚本化、可持久化），
而不是"多加几个命令词"。

⇒ 因此 L2 唯一值得探索的方向是**反向**：让 mod **读** App 的内部状态
（如"当前是否回放 / 剩余张数 / UI 焦点"）。但其中大部分可用 `capdtm getusr` 替代 ⇒ **优先级低**。

## 5. L3：p7 层 —— 真正的金矿

### 5.1 候选清单

| # | 候选 | 机制 | 收益 | 成本 | 风险 | 备注 |
|---|---|---|---|---|---|---|
| 1 | **A1 归一化器扩域** | `0x510b0` 重定向 + 24B 恒等特判块 | 全 7 维一键 | 已出包 | 中 | 🔶 待上机 |
| 2 | ★ **归一化器"扩表"（不止 4 个 id）** | 把恒等特判块升级为**查表**：加一张「外部 id → 内部 id」映射表 | **一次投入打开一批 id** | 中（与 A1 同量级） | 中 | ❓ **本轮最重要的候选** |
| 3 | ★ **PW 档位池外部写** | 外部直接写 p7 参数槽 `0xda..0xe2` | 绕开"档位应用需 App 确认" | 高 | 中 | 需要新增"外部→槽"通路 |
| 4 | ★★ **ISP tuning 参数开放（184 个 `eIQ_ID_*`）** | 扩大 `FUN_000d6b20` 可达 id 空间 | **7 维 → 184 维** | 极高 | **高** | 见 §5.3 |
| 5 | LUT 表直灌 p7 | 替换内置 4 组 LUT 缓冲 | 成片直灌 | 中 | 中 | ⛔ 已判死路（拍片流程会重配置档位池） |
| 6 | 内置 LUT 表批量替换 | 换掉出厂 LUT 表 | 画质风格 | 中 | 低 | 静态替换，可逆性差（需重刷） |

### 5.2 ★★ 候选 2 是"杠杆最大的一步"

A1 目前的做法是**特判 `0x130–0x133` 四个 id**（硬编码 `sub/cmp/bhi`）。
但同一个机制可以泛化成**查表**：

```
外部 id → [归一化表] → 内部 id       （现在：47 项，输出不含 0x130-0x133）
                 ↓ 越界
         [A1 特判块：4 个恒等]
                 ↓ 泛化后
         [扩展表：任意「外部 id → 内部 id」对]
```

- **成本**：与 A1 同量级（改 1 条 `b` + 写一块表 + 一个查表循环）
- **收益**：**一次投入，开放一批 id**，而不是每次为 4 个 id 打一个补丁
- **前提**：先要知道**有哪些内部 id 值得开放**（这正好由 §3.2 的 `iqr` 只读探测来回答）

> ⇒ **推荐路径**：先用零补丁手段（`iqr` + `mcbtest`）**测出"哪些内部 id 真的是活的"**，
> 再决定扩表要包含哪些 —— **先测后打，避免盲目扩域**。

### 5.3 候选 4（184 维）要谨慎 —— 为什么

- 诱人之处：`tuning_keys.txt` 有 **11,140 键 / 184 个 `eIQ_ID_*`**，等于把"7 维画面调节"扩成"整机 ISP 调参"
- 但风险不对称：
  1. **耦合**：ISP 参数之间有依赖（改 A 可能被 ISP 用 B 重算覆盖）
  2. **不可判**：现在的唯一客观判据 `iqr` 只能"读回"，**不能证明"被消费"**（这正是 G5-3 至今 BLOCKED 的原因）
  3. **爆炸半径**：写坏一个 tuning 参数可能让出图异常，而判据不明
- ⇒ **建议先做"只读映射"**：把 184 个 id 与**画面行为**建立对应（哪些真的影响出图、哪些是死参数）。
  这一步零风险，且是后续任何写入的前提。

## 8. 我的判断（结论与建议排序）

1. **现在最该做的不是写新补丁，而是"补 L0"** ——
   `mcbtest` + 未接线的 App 命令（质量/RAW、录像 pause、WB、可拍查询）成本极低，
   可能直接消掉 3–5 个"以为要补丁"的需求。**建议作为相机上线后的第一个新波次（W-7 探针波次）**。

2. **p7 层的重点应从"A1 那 4 个 id"转向"扩表机制"（候选 2）** ——
   A1 本身价值有限（只解决 R/G/B/HUE 四维），但它是**机制的第一次落地**；
   把它泛化成查表，才是"一次投入、长期可用"的做法。

3. **184 维 tuning 不要急着写** —— 先做只读映射（零风险），
   否则会重演 G5-3 那种"值变了但无法证明被消费"的困境。

4. **App 层继续加命令优先级最低** —— 通道已经开了，加词不加能力。

5. **任务流建议新增一个"W-6 能力探针波次"**（只读为主）：`mcbtest` 逐条试 MCB 命令字典 +
   `iqr` 前后比对 ⇒ 产出"零补丁可得能力清单" ⇒ **再决定 p7 补丁的靶子**。
