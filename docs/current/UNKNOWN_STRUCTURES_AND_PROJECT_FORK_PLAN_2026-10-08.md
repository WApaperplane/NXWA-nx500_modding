| **p8** | **rtos_data** | 52,427,776 | OK | **100.00%** | **非零字节 0 个，彻底全零** ⚠️⚠️ |

★★ **两条被这条证据推翻/动摇的现有表述**：

1. **`MANIFEST.txt` 与 `slp_crosscheck.txt` 把 `p3` 标为「出厂偏好 ★回滚用」** ——
   ★ **但 p3 备份实际是全零，它不可能作为任何东西的回滚源。**
   ⇒ 「p3 可回滚」这个说法在当前证据下**不成立**。
2. **`p2`（pref）备份几乎全零** —— 但 `pref` 是我们 **`prefman` 一直在写、且实机验证过持久化**的分区。
   ⇒ ★★ **两者必有一错**：要么备份读错了区域，要么"pref 写在 p2"这个模型本身有问题
   （数据可能实际落在 `p5` —— 它确实有 ~4.4 MB 真实内容，且与 `p1` 逐字节相同）。

> ★ **纪律提醒（对应铁律 94 / 116）**：不要去推"p8 里存着 p7 的参数"了 ——
> **在解释清楚"为什么这三个分区读出来是全零"之前**，"p8 是空的"这个观测
> **既不能证明"分区是空的"，也不能证明"里面没有东西"**。
> 三种可能未区分：**(a) 分区真空；(b) dd 读错区域（对齐/偏移）；(c) eMMC 对该区域有读保护**
> —— 同一条 `dd` 通路在 p7/p1/p5/p6/p13/p12 上**读得出真实内容**，所以 (b)/(c) 概率不高但未排除。
> ⇒ **必做**：拿一个已知非空的分区做对照重读，并对 p3 换偏移/换块大小再读一次（零风险，PC 侧 + 一次上机）。

而 `NX-Lantern` 只装得下后者、`D5Lab` 只装得下"平台"。

★ 用之前请自查一次：GitHub org/仓库名、PyPI、域名、以及 `metol` 在相机领域是否已被注册。

### 3.4 迁移动作清单（可直接执行）

1. 建 org（如 `metol-nx`）与 3 个空仓
2. **重起历史，不带 272 MB 旧 `.git`**：从 `nx-ks2` 按目录抽取（`git filter-repo --path scripts/ …` 或直接 rsync 首个提交）
3. 给产品加 **`VERSION`**（当前血脉 = NX-KS 2.88）+ 首次 release tag —— 现在 mod 是**无版本号**发布的
4. ★ **把铁律变成 CI**：对 `scripts/**/*.sh` 跑 `sh -n` + **`assert b'\r\n' not in data`**（CRLF 是铁律 99、本项目排查最久的一次）→ 这一条就能立刻提升质量
5. 补 **LICENSE + ATTRIBUTION**：写清「派生自 `nx500_nx1_modding`(AGPL) + NX-KS(KinoSeed，许可证待考)」，
   **在做完许可证审计前，不要把它包装成"全新原创项目"**
6. 证据基座进私有仓 / Release assets
7. 旧 fork 保留但标 `ARCHIVED` 或仅留同步用途
