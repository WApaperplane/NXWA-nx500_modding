## 2. 三态 + 两特例：为什么不能只用"通过/不通过"

| 状态 | 含义 | 处理 |
|---|---|---|
| `PASS` | 现在就能判，且满足 | 放行 |
| `FAIL` | 现在就能判，且**不满足** | **必须修**，不许带着红门上机 |
| `BLOCKED` | **还没到能判的时候**（依赖上机产物 / 上游门未过） | 不是失败，是"等" |
| `MANUAL` | **只能由人在机身判定**（铁律 104：进程活着 != 系统没被拖垮） | 工具挂出来，不代签 |
| `INFO` | 纯诊断，**不参与聚合** | 仅展示 |

★ `BLOCKED` 与 `FAIL` 必须分开：若把"等上机"也算红，上机前满屏红，门控会被下意识忽略。
★ 聚合优先级 `FAIL > BLOCKED > MANUAL > PASS`：BLOCKED 比 MANUAL 更上游（连上机的机会都还没有）。
★ `INFO` 是必需的：没有它，一个超时的旁证端口会被渲染成 `[ OK ]`，读起来像"它没事"——误导性输出。

★ 第 8 项的覆盖范围本轮已扩到 `test_server/u1/`（原先只查 `scripts/`）。
自证方式：往该目录塞一个 CRLF 文件，CI 立刻报
`FAIL CRLF [铁律99] test_server/u1/_crlf_selftest.sh`，随后删除。

## 5. 证据文件契约（要手写这四个，门才可能转绿）

### 5.1 `raw8/gates/u1/mem_compare.json`（G2 的唯一输入）

```json
{
  "ts": "2026-10-08T17:20:00",
  "method": "sh u1_rd.sh <idx>  =  dd if=/dev/mem bs=4 count=768 skip=addr/4",
  "addresses": {
    "0x94000000": {"readable": true,  "bytes": 3072, "dd_rc": 0, "md5": "...", "note": "阳性对照"},
    "0x2082b000": {"readable": false, "bytes": 0,    "dd_rc": 1, "err": "..., ", "note": "阴性对照"},
    "0x810fd100": {"readable": null,  "note": "问题本体：p7 LUT 缓冲 A"},
    "0x81115200": {"readable": null,  "note": "问题本体：p7 LUT 缓冲 B"}
  }
}
```
★ 四点必须齐全，否则 G2 保持 `BLOCKED`——**铁律 119**："地址面无 X"必须附地址面完整性证明。

### 5.2 `raw8/gates/u4/acceptance.json`（G4-1）

```json
{"ts":"...","slp_sha256":"...","minimal_change":"1 byte @0x000000","accepted":true,
 "telnet_alive_after":true,"entry":"Settings3>DeviceInfo>FirmwareUpdate>Body","notes":"..."}
```
门判的是 `accepted ∧ telnet_alive_after`（后者是安全网：改 p7 画面异常但 telnet 仍活）。

### 5.3 `raw8/gates/u5/rollback_drill.json`（G4-2）

```json
{"ts":"...","partition":"p7","drills":1,"ok":true,"restore":"dd from emmcbak/p7.bin"}
```
门判的是 `drills ≥ 1 ∧ ok`。★ **boot0/boot1 绝不碰。**

### 5.4 `raw8/gates/u1/iqr_dump.txt` 与 `iqr_epmc_map.tsv`（G5-2 / G5-3）

- `iqr_dump.txt`：机上 `st cap iqr` 的原始输出，唯一 `eIQ_ID_*` 数须 ≥184。
  ★ 少于此数先怀疑**被截断**（铁律 94：截断输出不能支撑统计），不要当成"判据不够"。
- `iqr_epmc_map.tsv`：`iqr(184 ID) × epmc(两块 21×10)` 的关联。
  ★ 必须记录**写入瞬间的运行时槽号**（U14：槽池 8 槽 × stride `0xc8`，槽号运行时分配）。

## 6. 本轮落地过程中发现的两条硬问题

### 6.1 ★★ `scripts/EV_MOBILE.sh` 处于"武装状态"（G1-2 FAIL）

| 文件 | md5 | 判定 |
|---|---|---|
| `scripts/EV_MOBILE.sh` | `55c47b8924342c422559b2181fa07c9f` | ✘ **社区"每 2s `ip addr ls`"死循环版** |
| `scripts/nx-rc/EV_MOBILE.sh` | `54a308b8c55d8e3a313f63c33e06d0a5` | ✔ 重写版 |
| `deploy/filmlab/EV_MOBILE.sh` | `2657352ebcadd6271f5c4e4332d3b1e6` | ✔ FilmLab 直达页版 |

`install.sh` 的两条路径都会把它原样装上机：全量安装 `cp -ar scripts -> /opt/usr/nx-ks`；
增量同步 `cp -ar /mnt/mmc/scripts/* -> /opt/usr/nx-ks/`。
⇒ **按一下 EV+WiFi 就会拖垮单核**。这不是"上机时才需要注意"，是**仓库当前状态本身就是隐患**。

建议修复（属产品决策，本轮**未擅自改**）：
`cp scripts/nx-rc/EV_MOBILE.sh scripts/EV_MOBILE.sh`，然后上机核对机上 md5 ∈ 上表两个安全值。

### 6.2 ★★ `epmc` 的 `nz` 模式里 `nreg` 是**结束下标**不是个数

`test_server/sysarch/epmc.c:107` —— `for (i = start; i < nreg; i++)`，其中 `start = from/4`。
所以"从 `0x1300` 起扫 512 个"必须写 `epmc 0 1728 nz 0x1300`（1216 + 512 = 1728）。

写成 `epmc 0 512 nz 0x1300` 会得到 `start=1216, nreg=512` ⇒ **循环一次都不执行**，
却照样打印 `NZ nonzero 0/-704`。这就是本项目最忌讳的**假结论形态：看着有输出，其实是空的**。
U1 包里的每条调用都已按此校正（`gate_pack_u1.py` 的 `EPMC_STEPS` 带"有效 regs"字段）。

## 8. 工具用法

```bash
# 状态板（默认联网探测）
python test_server/tools/gate_flow.py

# 纯离机判定（不碰网络）
python test_server/tools/gate_flow.py --no-probe

# 只看某几道门 / 落盘 JSON / 附 U1 runbook

# 生成 U1 只读上机脚本包（带自检）

# 上机后回收结果（PC 侧，FTP 21 端口，root 空密码，>60KB 自动分块）
```

★ **工具只读**：不写相机、不写固件、不发任何非只读命令。上机动作全部由 runbook 的人工步骤驱动。
