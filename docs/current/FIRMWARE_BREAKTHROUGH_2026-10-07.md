## 〇、★★★★★ 三处前置结论修正（★ 最重要的部分）

本次深挖推翻/修正了三条此前写进记忆的结论。**它们决定了整个魔灯路线的可行性判断。**

### 修正 1 ★★★★★「p7 里没有 EP 物理基址字面量」——**错误**

| 旧结论（2026-10-06） | 本次实测 |
|---|---|
| `0x20821c00` / `0x2082b000` / `0x20820000` 在 p7 镜像中**出现 0 次** | ★ **伪代码里直接出现**：`20820000`×16、`20821c00`×3、`2082b000`×4、`20824000`×1、`2083xx`×230 |

**根因**：旧结论用的是**字符串/定义标量搜索**（`31_ep_access.txt` 查的是"值为该地址的已定义标量"），
而 EP 地址在代码里是**编译进指令的立即数**（`*(uint*)(iVar+0x20821300)=...`），
**不是数据段的标量** ⇒ 搜索通路本身错，结论自然错。

⇒ ★★ **这正是铁律 32 的镜像**：「找不到 X」不能推出「不存在 X」，**除非先证明搜索通路有效**。
　本次换了通路（在反编译产物里 grep），立刻命中。

### 修正 2 ★★★★★「p7 是 EP 的并列消费者，不驱动 EP」——**错误**

| 旧结论 | 本次实测 |
|---|---|
| EP 寄存器「只由 UDD 驱动」（Linux 侧） | ★★ **p7 直接写 EP 寄存器**：`FUN_004b6894` 写 `0x20821300`–`0x20821328`（10 个寄存器）|

**⇒ p7 和 Linux 是 EP 的【两个并列写入者】，不是「驱动 / 被驱动」。**
　这**大幅提高**了魔灯的可行性：p7 侧有现成的参数下发函数，不必从零造。

### 修正 3 ★★★★★「3D LUT 寄存器映射只有 Linux 侧一个来源」

| 旧结论 | 本次实测 |
|---|---|
| 3DLUT 寄存器语义来自 Linux 侧反汇编 | ★★ **p7 侧独立复现且完全一致**（§3）|

⇒ 两个独立来源交叉验证 ⇒ **3DLUT 寄存器映射从"单源推测"升级为"双源确证"**。

## 一、★★★ 本次核心发现：p7 的 ISP 参数下发块（已完整解出）

### 1.1 ★★★★ `FUN_004b6894` / `FUN_004b6b98` —— 现成的 ISP 参数写入器

这是本次**最有价值的发现**：两个函数完整实现「**参数索引 + 参数结构体 → EP 寄存器块**」的转换。

```
FUN_004b6894(param_1, param_2, param_3)     @0x4b6894 / 760B / 28 调用者
  param_1 = 参数索引 (0x00..0x14 = 21 个槽)
  param_2 = 参数结构体指针 (uint 数组)
  param_3 = 0 / 1 (双缓冲选择)
  ⇒ iVar17 = (param_3 ? 0x80 : 0) + param_1 * 0x100
  ⇒ 写 0x20821300 + iVar17 .. 0x20821328 + iVar17   （10 个寄存器）

FUN_004b6b98(param_1, param_2, param_3)     @0x4b6b98 / 688B / 27 调用者
  ⇒ 同构，目标块 = 0x20821700   （另一路，大概率 View / Still 双通路）
  ⇒ 末尾 FUN_004ba6a8((param_1) + 4 & 0xff)  ← 索引偏移 +4
```

★ **寄存器映射 = `base + slot*0x100 + {00,04,08,0c,10,18,1c,20,24,28}`**
⇒ 每个参数槽占 **0x100 = 256 字节**，21 个槽 ⇒ `0x20821300` 块共 **21×256 = 5376B ≈ 5.25KB**。

### 1.2 ★★★★ 参数结构体的**位域布局**（★ 这是"参数值表布局未知"的正面回答）

`param_2` 指向的 `uint[]`，字段打包方式（从伪代码逐位解出）：

| 源 | 目标寄存器 | 位域打包 |
|---|---|---|
| `param_2[0]` | `+0x00` | 直写（低 4 位须为 0，作校验）|
| `param_2[1]` | `+0x04` | 直写（低 4 位须为 0）|
| `param_2[2..4]` 组合 | `+0x08` | `(p2[2]&0x7ffff)<<0xc` \| `((p2[3]-8)>>1 &7)<<8` \| `(p2[4]&3)<<6` \| `(byte@0x11 &3)<<4` \| `(byte@0x12)&3` |
| `param_2[6]` | `+0x0c` | `原值 & 0xc00fffff \| (p2[6]&0x3ff)<<0x14` |
| `param_2[7],byte@0x1d..0x1f,param_2[0x12]` | `+0x10` | 多个 1/2/4-bit 开关位 |
| `param_2[0xd],param_2[0xc]` | `+0x18` | `(p2[0xc]<<0x10) \| (p2[0xd]&0xffff)` |
| `param_2[9],param_2[8]` | `+0x1c` | `(p2[8]<<0x10) \| (p2[9]&0xffff)` |
| `param_2[0xb],param_2[10]` | `+0x20` | `(p2[10]<<0x10) \| (p2[0xb]&0xffff)` |
| `param_2[0xf],param_2[0xe]` | `+0x24` | `(p2[0xe]<<0x10) \| (p2[0xf]&0xffff)` |
| `param_2[0x11],param_2[0x10]` | `+0x28` | `(p2[0x11]&0xff)<<8 \| (p2[0x10]&0xff)` |

⇒ ★★★★★ **「参数值在哪、怎么打包」这条最难的静态问题，对这两个块已经有答案了。**
　这**直接推翻了** `p7-isp-slp.md` §3 里「参数值表位置未知、只能改 p7 赌一把」的判断
　—— 至少对 **`0x20821300` / `0x20821700` 两个块**，收发表格已经解出。

### 1.3 ★★★★ `FUN_0017adf4` / `FUN_0017ae08` —— 单参数寄存器对写入器（★ 接口形状最清晰）

```
FUN_0017adf4(param_1, param_2, param_3, param_4)   @0x17adf4 / 180B
  校验：param_2 必须 < 0x2（即 0 或 1）；param_1 & 0xff 须 < 0x80
  ⇒ iVar1 = (param_3 ? 0x80 : 0) + param_1 * 0x100
  ⇒ FUN_004ba5fc(idx, 1)                    ← ★ 加锁 / 选页
  ⇒ 写 0x20821300+iVar1 = param_2[0]
  ⇒ 写 0x20821304+iVar1 = param_2[1]
  ⇒ FUN_004ba5fc(idx, 2)                    ← ★ 解锁 / 提交
```

★★ **这就是一个"命令式接口"**：`(索引, 值对, 双缓冲选择, 报错码)`。
　它**比 `FUN_004b6894` 更适合做注入点**——因为它只写 2 个寄存器、有锁保护、有明确的 ID 语义。

### 1.4 ★★★ 调用链：这两类写入器挂在**命令分发**下

```
FUN_00110eb0(param_1,param_2,param_3,param_4)   @0x110eb0 / 76B
   = 薄包装 → FUN_0017adf4(param_3, param_4, param_2)
   = 错误时走 FUN_00173f34(...,0x10000001,...)   ← 标准 FE_RESULT 错误上报
   ↑ 被 7 个 0x111xxx–0x127xxx 的函数调用（命令处理器簇）
      FUN_00115d30 / FUN_00116414 / FUN_0011b1c0 / FUN_0011bd10
      FUN_0011debc / FUN_0011e9c0 / FUN_0012708c
   ↑ 这 7 个的调用者 = 0（静态收敛）⇒ ★★ 它们是【间接调用】的
```

**间接调用 ⇒ 存在函数指针表 / 命令表。** 但全镜像搜索这 7 个 handler 的地址：
- 4 字节小端编码：**0 处命中**（ARM 与 Thumb 编码都试过）
- Thumb `BL` 直接调用：**0 处命中**

⇒ ★★★★ **判决：p7 的命令分发【不存裸地址】。**

## 二、★★★★ p7 的分发机制：**ARM 索引跳转表**（★ 本节结论已被 2026-10-07 20:20 修正）

> ⚠️ **更正**：本节原判「veneer 桩 / 架构上不存裸地址」**是错的**。
> 详见 `docs/current/P7_DISPATCH_AND_LSC_2026-10-07.md`。要点：
> `FUN_003f3fa4` 是 **ARM `cmp r1,#0x13; ldrls pc,[pc,r1,lsl #2]` 索引跳转表**（20 条，id 0..19），
> 目标存 **MMU 虚拟地址**（`0x803f40XX`）；旧分析用 Thumb 模式误读 ARM 指令 ⇒ 凭空造出"7 条 veneer"。

`gamma_writer_hunt` / README 都提到「`FUN_003f3fa4` 是 veneer switch，Ghidra 解不出」。
本次用 capstone 手工解出来了（**ARM 模式**）：

```
FUN_003f3fa4(param_1, param_2)   @0x3f3fa4
   0x3f3fa4: cmp     r1, #0x13             ← id <= 19
   0x3f3fa8: ldrls   pc, [pc, r1, lsl #2]  ← ★ ARM 索引跳转表
   0x3f3fac: b       #0x3f40a0             ← 默认: mov r0,#0; bx lr（返回 0）
   0x3f3fb0: .word   0x803f4098            ← table[0]（VA 基址 0x80000000）
   ...
0x3f3ffc:   .word   0x803f4000             ← table[19]
```

**⇒ 每个 handler = `ldr r0,[r0,#0x14+id*4] ; bx lr`（单指令字段取值桩）**
⇒ 语义 = 读 struct 的 20 个 u32 字段（`+0x14..+0x60`），id 越界返回 0。

★ **推论（可当铁律用）**：
> **裸镜像里"找不到函数地址表"时，先检查：(a) 指令集模式对不对（ARM/Thumb 混编易误读）
> (b) 表里是不是 MMU 虚拟地址（高位置 1）。两条都不成立，才怀疑"表被删了 / 架构上不存"。**

★★ **换言之：p7 确实存裸地址（在跳转表里），只是以 MMU VA 形式、且需 ARM 模式解码。**
★ 副产品：同族访问器解出 p7 的**镜头阴影（LSC）表生成器** `FUN_003f2f64`（见新文档 §2）。

## 三、★★★★ 3D LUT 寄存器映射：p7 侧独立复现（★ 双源确证）

p7 侧 3DLUT 访问函数（`ps_scan.py ep` 全表）：

| 函数 | 目标 | 语义（p7 侧反编译） |
|---|---|---|
| `FUN_004cf3d4(1)` | `+0x000` | `reg \|= 1` / `reg &= ~1` ⇒ **OnOff（bit0）** |
| `FUN_004cf3fc(v)` | `+0x004` | `reg = reg&~3 \| v&3` ⇒ **SelCbCr_ch = bits[1:0]** |
| `FUN_004cf414(v)` | `+0x004` | `reg = reg&~0x30 \| (v&3)<<4` ⇒ **SelLUT = bits[5:4]** |

⇒ ★★ **与 Linux 侧（`docs/current/3DLUT_DEEP_DIVE_2026-10-07.md`）逐位完全一致**：
　`+0x000 bit0 = OnOff`｜`+0x004 bits[1:0] = SelCbCr`｜`+0x004 bits[5:4] = SelLUT`。

★★★★★ **这是本项目第一次出现「同一寄存器映射由两个独立来源（Linux 反汇编 + p7 反编译）确认」。**
⇒ 3DLUT 寄存器表从「单源推测」升格为「双源确证」，**可放心作为魔灯 LUT 通路的基准**。

## 五、★★★★★ 魔灯路径重评估（三条路，按"可验证性"排序）

**判据来源：铁律 86（固件层准入门槛 = 该参数必须先有生效判据）。**
**门槛不是"能不能改"，而是"改完能不能验证"。**

| # | 路径 | 机制 | 生效判据 | 可逆性 | 结论 |
|---|---|---|---|---|---|
| **A** | **3D LUT（Still 路径）** | `CBackend_3dlut_Still` + WDMA 硬件 DMA | ✅ **画面变化（已验证通路）** | ✅ 无需刷固件 | ★★★★★ **主力路线，已在用** |
| **B** | **ISP 参数块 `0x20821300/1700`** | p7 侧 21 槽参数下发（本次解出） | ⚠️ **需先建立判据**（`iqr` 是否含？） | ✅ **无需刷 p7**（寄存器直写） | ★★★★ **最有潜力的扩展** |
| **C** | **改 p7 固件本体（gamma/color）** | 改值表 / 改指令 | ❌ **无判据**（`iqr` 197 行不含 gamma/color/NOG） | ❌ 不可逆 + 只能刷官方整机 | ⛔ **按铁律 86 冻结** |

### ★★★ 路径 B 是本次真正的"突破口"——理由

1. **不用刷固件**：`0x20821300/1700` 是 **EP 寄存器**，Linux 侧可 mmap 直写（已验证 3DLUT 同理）
2. **参数布局已知**（§1.2）⇒ 不是"赌一把"，是"按表填数"
3. **p7 侧有现成下发函数**（`FUN_004b6894` 等）⇒ 语义清晰，不必从零逆向
4. **有潜在判据**：这 21 个槽大概率对应 `iqr` 的 184 个 `eIQ_ID_*` 中的一部分
   ⇒ ★ **只需跑一次 `iqr` 对照，就能确定"哪些槽有客观判据"**（纯 Linux 侧，零刷写风险）

### ★★★★ 路径 B 的可行性判定实验（**下一步 P1，零风险**）

```
① 上机跑 iqr，dump 全部 184 个 eIQ_ID_* 的当前值        （只读）
② 用 epmc.arm 读 0x20821300/1700 两个块的 21×10 寄存器   （只读，≤768 regs 限额内）
③ 本地关联：iqr 的哪些 ID = 这两个块的哪些槽             （PC 侧比对）
④ 判据成立 ⇒ 路径 B 可解，设计"寄存器直写配方"
   判据不成立 ⇒ 路径 B 降级，退回路径 A（3D LUT）
```

⇒ ★ **这一步不做任何写入、不刷任何固件、不违反铁律 86 ⇒ 可以立刻做。**
