# SLP 固件容器格式（★ 全解 · 2026-10-08）

> **U12 结案。** 这是「改 p7 后能不能刷回去」的唯一闸门。
> 本文给出**逐字段格式 + 校验算法 + 可复现脚本 + 实测三方一致性证明**。
> 样本：`.uploads/fw/nx500_v1.13.bin`（352,121,435 B）｜脚本：`raw8/fw/slp_parse.py`｜报告：`raw8/fw/slp_parse_report.txt`
>
> ★★ 前一轮的结论「记录不是定长、stride 28 只中 1/10、布局未解」**已推翻** —— 真正的步长是 **24**，
> 而且**根本不是靠猜**：用十个已知镜像长度当小端 u32 回搜，命中位置自己排出了 24 的等差。

---

## 0. 一句话结论

> **SLP = 48B 头 + 16B 标签 + N×24B 记录表 + N 段连续镜像，无任何签名，只有 JAMCRC。**
> ⇒ **可以离线重打包，并且校验可算。** p7 恰好是**没有内层自校验的原生 ARM 块**（img5），
> 是最容易重打包的一条。**闸门开了，但"刷得进去"仍需机上验证一次**（见 §6）。

---

## 1. 全局布局

```
偏移        内容
0x00        SLP 头（48 B）
0x30        标签（16 B）  ← "\x01VER_PR1\0…"，全容器仅此一处名字串
0x40        记录表：N × 24 B（N = 头里 num_image）
0x40+24N    img[0] 起始 —— ★ 与记录表**严格首尾相接**，无对齐填充
…           各镜像**连续平铺**，第 i 段 = [off_i, off_i + len_i)
EOF         恰好等于最后一段的结束（无尾部填充、无签名块）
```

**实测（v1.13）**：`0x40 + 24×10 = 0x130`，而 0x130 处正是 `27 05 19 56`（uImage magic）。
文件末尾 `0x14FCF25B` = 352,121,435 = 文件实际长度 —— **分毫不差**。

## 2. SLP 头（48 B）

| 偏移 | 长度 | 字段 | v1.13 实测值 |
|---|---|---|---|
| 0x00 | 4 | magic | `"SLP\0"` |
| 0x04 | 8 | `version_user` | `"1.13"` |
| 0x0C | 16 | `project` | `"NX500"` |
| 0x1C | 16 | `version_date` | `"NX500GLU0APC1"`（★ 不是日期，是机型/产线/批次码）|
| 0x2C | 4 | `num_image` (u32 LE) | `10`（与 raw8/fw 里 slp00–slp09 十个文件吻合）|

## 3. 标签（0x30，16 B）

```
01 56 45 52 5f 50 52 31 00 00 00 00 00 00 00 00
│  " V  E  R  _  P  R  1"
└─ 前导 0x01（含义未定：可能是"标签数"或版本档位）
```
全容器**只有这一处名字串**。⇒ 镜像**没有名字字段**，只有长度/偏移/CRC。

## 4. 记录表（步长 24 B，10 条）

每条记录（全部小端）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| +0x00 | 4 | `len` | 该镜像字节数 |
| +0x04 | 4 | `crc` | ★ **JAMCRC**（见 §5）|
| +0x08 | 4 | `offset` | 该镜像在 SLP 文件中的绝对起始偏移 |
| +0x0C | 4 | `flags` | 语义**未定**（见 §4.2）|
| +0x10 | 8 | `tail` | 一般全零；**img1 处为 ASCII `"BABF43A\0"`**（可疑是短版别/客户码）|

### 4.2 flags 语义未定 —— 但有一个**极显眼**的阶梯

```
idx0 FF FF FF FF      idx5 FF 0F 10 32
idx1 FF FF FF 7F      idx6 FF 00 00 21
idx2 FF FF FF 65      idx7 0F 00 00 10
idx3 FF FF 3F 54      idx8 FF FF FF FF   ← 与 idx0 相同
idx4 FF FF 21 43      idx9 FF FF FF 7F   ← 与 idx1 相同
```
idx2→idx7 呈 `65FFFFFF → 543FFFFF → 4321FFFF → 32100FFF → 210000FF → 1000000F` 的**半字节阶梯**，
且 idx8/idx9 复用 idx0/idx1 的值。**结论：不是校验、不是长度、不是偏移** —— 更像厂商侧某个
「板级/产线配置位图」被逐条递减写入（甚至可能是未初始化残留）。**不影响重打包**（不参与平铺与 CRC）。

## 5. 校验算法（★ 唯一的一个）

**每个镜像段**独立算一次 **JAMCRC**：

```python
import zlib
def jamcrc(b: bytes) -> int:
    return zlib.crc32(b) ^ 0xFFFFFFFF     # 反射 CRC-32，初值 0xFFFFFFFF，**不做最终异或**
```
- 10/10 全部命中记录里的 `crc` 字段（`raw8/fw/slp_parse_report.txt`）
- **standard CRC-32（`zlib.crc32` 直接结果）10/10 全不中** ⇒ 判据是排他的，不是巧合
- 覆盖范围 = `d[offset : offset+len]`，**逐条独立**，不跨段、不含表与头
- ★ **SLP 里没有签名块**：文件末尾与最后一段严格重合，不存在尾部摘要/证书区

## 6. 由此得到的重打包配方（★ 待机上验证）

```python
# 1) 改 p7：SNL img5 段内 byte 0x200（= 段首起算）
seg = bytearray(d[0xef4301 : 0xef4301 + 12075648])
seg[0x200] = 0x11
# 2) 回填该段
d[0xef4301 : 0xef4301 + 12075648] = seg
# 3) 重算**该段**的 JAMCRC，写回记录 5 的 crc 字段（偏移 0x40 + 5*24 + 4）
struct.pack_into("<I", d, 0x40 + 5*24 + 4, zlib.crc32(seg) ^ 0xFFFFFFFF)
# 4) len / offset 不变（等长替换）⇒ 其余 9 段、头和表都不用动
```
★ **等长替换 + 只改一个 CRC 字段**，是本格式最容易做对的一类改造。

**仍必须机上验证的（闸门之外的部分）**：
1. 相机 `Settings 3 → Device Information → Firmware Update → Body Firmware Update`
   是否接受**被改过的 SLP**（有无本项目尚未发现的二级校验，如 `libfirmware-upgrade.so` 里的白名单/机型串比对）。
2. SLP 内 img5 的 p7 与分区 p7 的关系：**是"原样落盘"还是"解包后再加工"**。
   实测两者**逐字节相同**（§7）⇒ 强烈指向"原样落盘"，但落盘路径仍需机上确认。
3. **恢复路径**：刷错了怎么办 —— 官方 SLP 在手（本文件），且分区备份在手（`raw8/emmcbak/p7.bin`）。

## 7. ★★★ 三方一致性（本轮最有价值的一条实测）

```
SLP img5（官方固件内）        md5 = 5fc4824f5b6a6a3caca1f9104238b8ac
分区 p7.bin[:12075648]（机上）md5 = 5fc4824f5b6a6a3caca1f9104238b8ac   ← 完全相同
p7_full.bin[:12075648]        md5 = 5fc4824f5b6a6a3caca1f9104238b8ac   ← 完全相同
p7_patched.bin                md5 = 1b29180b0abff2161c89a7b0245097ec   ← ★ 只差 1 字节
```

| 结论 | 依据 |
|---|---|
| **两条完全独立的官方来源字节相同** | 机上 `dd` 备份 与 官方固件 SLP 内嵌 ⇒ 官方 p7 镜像 = `5fc4824f…` |
| ★ **`p7_patched.bin` 的 0x200 改动不是任何官方来源** | 三方比对，差异字节仅 `0x200`（`10 0f 03 ee` → `11 0f 03 ee`）|
| ★ **`p7_full.bin` = 官方镜像 + 尾部补零到 12.25MB** | 其 `[0:12075648]` 与官方同位 md5 相同；`[12075648:12845056]` 全部为 0 |
| ⇒ **`p7_patched.bin` 的尺寸 12,075,648 = p7 的"真实长度"** | 等于 SLP 记录 5 的 `len`；也等于分区「最后一个非零字节所在段」 |

⇒ 因此 `p7_patched.bin` **不是"截断的下载"**，而是**「从官方容器里取出 p7 后改了 1 字节」**。
（`MANIFEST.txt` 里"p7_full 是 12.25MB 片段"的说法也随之精确化：它是**补零**到 12.25MB 的。）

### 7.1 那 1 字节到底改了什么（ARMv7 反汇编）

```
800001fc  e59f0054  ldr  r0, [pc, #0x54]      @ 0x80000258 = 0x55555555
80000200  ee030f10  mcr  15, 0, r0, cr3, cr0, {0}   ← ★ 原版：写 DACR（域访问控制）= 0x55555555（16 域全 client）
80000204  f57ff04f  dsb  sy
80000208  ee070f18  mcr  15, 0, r0, cr8, cr7, {0}   ← TLBIALL（用同一个 r0）
8000020c  ee070fd5  mcr  15, 0, r0, cr7, cr5, {6}   ← 失效整个分支预测阵列
80000210  f57ff04f  dsb  sy
```
补丁把 `{0}` 改成 `{1}`（opcode2 0→1）。**ARMv7-A 架构里 CP15 c3/c0/op2=1 未定义**
（本镜像确实是 ARMv7：`f57ff04f = DSB SY` 是 ARMv7 指令）⇒ 该写入要么不生效、
要么触发**未定义指令异常**。两种后果都指向同一件事：

> ★★★ **这一字节是"复位期域权限配置被破坏"，不是可用的功能补丁。**
> （DACR 若停在复位值，域 0 由 client 变成 no-access ⇒ 第一次被域 0 管辖的访存就 fault。）
> ⇒ **该文件只应作为"考古样本"保留，绝不能拿去刷机。**
