# UI 框架替换可行性分析：换掉 EFL 能否支持滤镜预览（2026-10-17）

> **同日后续实机新证据**：小面积、按需重绘的 Nuklear / X11 / Xft 独立界面已跑通，
> 用户确认面板可见、取景/按键正常，并确认不同配方的实时色彩变化；现已接入菜单。
> 见 [NXUI_NUKLEAR_2026-10-17.md](NXUI_NUKLEAR_2026-10-17.md)。
> 因此下文基于此前全屏试验得出的“不换框架”建议已经过时；全屏失败仍是历史事实，
> 不能据此否定本次小面积、事件驱动的替代界面。取景仍由相机原有管线输出。

> **问题（木一）**：能不能改掉当前 NXKS 基于 Enlightenment（EFL）工具包的 UI，用另一种开源框架，以支持滤镜预览效果？
> **性质**：离线分析 + 工作树实验对照；引用既有实证 + 本轮 rootfs/真机只读采集；**零写机**。
> **口径**：✅ = 已实机验证 ｜ 🔶 = 待上机 ｜ ❓ = 未证 ｜ ⛔ = 已实测证伪
>
> **结论前置（三句话）**：
> 1. 「滤镜预览效果」由 p7/EP **硬件链路**提供（PW 直推 + LUT1 直灌），**与 UI 框架无关**——它已经在，且作用于整个取景屏；UI 的任务只是「选择 + 触发 + 状态显示」。
> 2. **换框架在「现代化小窗口」形态下可行**——工作树中已有 **Nuklear + Xlib + Xft** 实验（`test_server/nxui/`，进行中）：小面板、事件驱动、队列防抖、**不碰取景 plane**、**零 EFL 依赖**（GLIBC 需求仅 2.4）。它绕开了三道墙，而不是撞上去。
> 3. **三道物理约束依旧成立**，它们定义了新框架的**可做范围**：小面板/选择器（✅ 可行）｜全屏自绘（⛔ 已实测拖死整机）｜UI 内预览窗格（⛔ 无帧源）。**新框架 ≠ 新能力**：它买到的是「开发体验 + 输入自由度 + 持久形态」，买不到任何系统级新能力。

## 1. 先把问题拆开：三个独立的层

| 层 | 提供者 | 现状 | 换 UI 框架能否改变 |
|---|---|---|---|
| **滤镜效果**（预览/成片） | EP/ISP 硬件链路：`d5_ep_3dl_load_lut`（官方 API，SEL_LUT_EXT）/ LUT1 通道 + 守护 / PW 直推 | ✅ 预览侧通（LUT：E1 接入 + E3 抢回；PW：全 7 维 A2 直推，10-15 双轮 PASS）；成片 LUT ❌（E4 负结论，定式=预览直灌+成片后处理） | **不能**——与 UI 完全无关 |
| **界面绘制**（窗口/菜单） | 原厂 `di-camera-app`（EFL+Edje）／`mod_gui`（EFL 小窗口，二进制）／`nxfilmui`（EFL 自绘实验）／**`nxui`（Nuklear，新）** | mod_gui 可用但「点击即关窗」；nxfilmui 全屏版 ⛔、轻量版未做；**nxui 已产出 host+ARM 二进制（待上机）** | **能换**——但只在小窗口形态（§3/§4） |
| **输入**（波轮/触摸/按键） | 内核先消费 + Xorg + `EV_*` 钩子族 | 钩子族在；**波轮发出的 keysym 未测**（wheel-E1）。mod_gui「只认 4 keysym」= 它自身二进制局限，**用源码在手的自写 UI 天然绕过**（nxui 已处理标准键 + 鼠标滚轮 4/5） | **不能改所有权，但能自行映射**（源码在手时） |

> ★ 一句话：**「预览」是硬件链路的账，「滚轮」是输入所有权的账，「界面」才是框架的账。三本账分开算。**

### 2.4 ★ 并行实验观察：Nuklear 面板（`test_server/nxui/` + `scripts/nxui.sh`，工作树进行中，未入库）

> 2026-10-17 08:35–08:42 间出现于工作树。本分析与之独立对照。

**设计要点（读源码所得）**：

| 要点 | 实现 | 对应约束 |
|---|---|---|
| 形态 | **底部面板**：条带 192px / 菜单 336px，居中吸底；`CWOverrideRedirect` 直管窗口 | 小窗口 ⇒ 绕开全屏资源墙 |
| 渲染 | Nuklear + **Xlib + Xft**（`NK_XLIB_USE_XFT`）；**事件驱动**，唯一定时器 = 防抖 | 绕开忙轮询（v8 教训） |
| 取景 | 注释明示：*"The viewfinder stays on its existing camera plane: **no frame capture or blit**"* | 绕开帧源与所有权问题 |
| 交互 | 标准 keysym（Esc/方向/Enter/KP_Enter）+ **鼠标滚轮（button 4/5）**；注释：*"Camera wheel mappings need measurement"* | 波轮映射待测（与 wheel-E1 同源） |
| 预览/保存 | 选中 → `filmlab.sh preview <key>`（防抖 250ms，仅 idle 时执行）；**Enter → `commit` + 退出** | 「滤镜预览」的正确交互语义 |
| 进程纪律 | fork + `setpgid` 隔离、关 X11 连接继承、超时管理、output 捕获 | 对齐项目现场纪律 |
| 生命周期 | `nxui.sh available/menu/filmlab/demo/stop`；`enabled` 开关文件；启动时 `killall mod_gui` | 替换 mod_gui 角色的定位 |
| ABI | `-nostdlib` + 相机 libc 直链 + 自备 crt0；**产线检查**：无 EFL NEEDED、GLIBC 需求 ≤2.4 | 完全符合相机工艺 |

**产物状态**：host 版（x86-64）+ **ARM 版 `out/nxui.arm`（436KB）** 均已编译；`needed.txt`/`versions.txt` 检查通过；模型层单测 `test_model` 已跑；Xvfb host 冒烟测试**未通过**（测试环境缺 `xkbcomp`，属 host 测试环境坑，不涉及 ARM 产物）。

**对该实验的三点独立判断**：

1. **路线判断：正确。** 它精确落在「唯一可能成立」的区间（小窗口 + 事件驱动 + 不碰取景 + 零 EFL），与本文 §3/§4 的约束推导一致；「preview/commit 分离」正是「滤镜预览」需求的直接实现。
2. **待验证三关（上机前必须过）**：
   - **显示关**：X11 共存（mod_gui 先例乐观，但 override-redirect 面板 vs di-camera-app 全屏存在 z-order/辅助进程盖屏史——U2 曾 killall focus_stack 类排查）→ 30s 观察 + 两轮负载（U2 纪律）；
   - **输入关**：**波轮实际发出的 keysym** 未测——需先测（xev/落盘探针），再把映射补进键处理；
   - **字体关**：Xft + fontconfig + CJK（`fonts.conf` 已备）；先用相机 SDIC 字体或另行验证。
3. **性能预估（保守）**：Nuklear 即时模式 + 软件 Xlib 渲染小面板，开销应远低于「全屏 GL」（v9 死因）；但 Xft 文本重绘的实际成本需实测——「不折腾相机主链」是硬判据。

## 3. 「换框架」成本表（更新：实测化评估）

| 候选 | 形态与路径 | 必趟的坑 | 判断 |
|---|---|---|---|
| **Nuklear**（nxui 实验） | Xlib+Xft，小面板，软件渲染 | ① 显示共存 ② 波轮 keysym 映射 ③ Xft CJK 字体 ④（已解决：ABI/依赖/构建工艺） | 🔶 **最有希望的候选，正在验证** |
| LVGL | 交叉编译 + 自写显示后端 | ①-③ 同上 + 无相机先例；显示后端接 `libdrm_drime5` 私有 DRM 或 X11 | 🔶 可行但工作量 > Nuklear（Nuklear 单头文件、无构建系统依赖、X11 后端现成） |
| SDL2 | 先移植本体 | 同上；无先例 | 不优先 |
| Qt / GTK | — | 资源/依赖/ABI 不现实 | ⛔ |
| 无框架（fb0 直写） | — | 与 Xorg/App 争屏（App 是 DRM master） | ⛔ |

> ★ **Nuklear vs EFL 的真实账**：获得的 = 源码在手（输入映射/布局完全自主）＋ 现代开发体验（单头文件、任意机器编译）＋ 持久面板（对比 mod_gui「点击即关窗」）＋ Xft 标准字体链；付出的 = 重趟显示/输入/字体三坑 + 新维护面。**若三关全过，这笔账是划得来的**（前提：限定小面板形态）。

## 4. 换框架**不能**解决的四件事（护栏，防止外推）

1. **资源墙**：全屏渲染 = 拖死整机（任何框架；表现=CPU/内存带宽/GPU 抢占）。
2. **屏幕所有权**：`di-camera-app` 为 DRM master；mod UI 只能小窗口（面板/叠加）。
3. **输入所有权**：按键先经内核/固件消费（长按/连击/组合键不可得）；「波轮发什么」待测——但**源码在手的 UI 可自行映射任何到达 Xorg 的事件**（这点 Nuklear 版优于 mod_gui 二进制）。
4. **取景帧不可得**：无 `/dev/video*`；**「UI 里嵌滤镜预览窗格」没有帧源**——最真实的预览就是取景屏本身（效果作用于整屏）。nxui 的「preview=调用引擎改变取景屏」才是正解。

| 路 | 内容 | 状态 | 备注 |
|---|---|---|---|

## 6. 结论与建议

1. **「换框架」的答案是分层的是**：全屏 ⛔｜**小面板 ✅（Nuklear 实验正在验证）**｜预览窗格 ⛔。不要用「能不能换」一句话概括，按形态分层判断。
2. **对 nxui 实验的支持态度与验收建议**：这是目前性价比最高的「UI 现代化」路线；建议按三关验收（§2.4）——**显示关（含 30s 观察）→ 输入关（波轮 keysym 实测）→ 字体关（Xft CJK）**，全过后再替代 mod_gui 角色，并以「enabled 开关 + killall 互斥」保证可禁用。
3. **路 A 不被替代**：原生三槽（含标签产品化）是**零成本、今天就能有**的形态；nxui 面板是增强形态（列表更长、驻留不关窗），两者可并行、可组合（面板调 `filmlab.sh preview`，最终效果落屏路径与 A 共用）。
4. **主线不受影响**：T3/T5/U7、「滤镜预览=硬件链路」的工程化（切换延迟测量、连续切换回归）照 GOALS 推进。
5. **边界提醒（护栏）**：后续无论用什么框架/形态，**不要外推**到全屏自绘、长列表钩挂 di-camera-app、UI 内实时帧预览——这三件已有明确负证据或结构性障碍。
