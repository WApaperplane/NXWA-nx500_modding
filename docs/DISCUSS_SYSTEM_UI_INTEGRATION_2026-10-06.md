# 探讨：放弃 mod_gui、集成进系统级 UI？

> 2026-10-06 · **纯探讨，未动代码**。基于 identity LUT 实机测试通过 + `mod_gui`/`loadgui.sh` 源码分析。
> 结论前置：★★ **"集成进系统 UI"这个方向我认同，但"放弃 mod_gui"是错的解法。**
> 真问题不是"要不要 mod_gui"，而是"**mod 的入口应该挂在哪一层**"。

---

## 0. 直接回答

| 问题 | 回答 |
|---|---|
| 能不做mod_gui 吗？ | ★★ **能，而且应该**（它是 14KB 的第三方 ELF，靠 `killall` 管理，进出靠按键钩子，层级很浅）|
| 应该"放弃"吗？ | ★ **不该**。它是目前**唯一已验证能跑**的交互载体。换掉它等于自找麻烦 |
| 正确做法是什么 | ★★★ **把 mod_gui 降级为"调试/兜底通道"，同时新增一条系统级常驻通道**。<br>两条通道并存，不是替代 |

## 1. 先把层级摆清楚（这是判断的基础）

```
┌─ 系统原生 UI（di-camera-app，EFL，机身原生界面）
│   ├─ 由 /usr/sbin/xxx 钩子脚本挂载功能
│   │   ★ EV_OK/UP/DOWN/LEFT/RIGHT/S1/AEL/EV.sh← 【这就是"系统级入口"】
│   │   ★ st app / st cap = 官方 CLI（无需 mod_gui 就能改系统状态）
│   └─ 内核 / ISP 先消费按键 ⇒ 长按/连击/组合键不可得（架构级）
│
├─ mod_gui（14KB 第三方 EFL 程序，靠 EV_EV.sh 起）
│   ├─ 菜单页 = 纯文本 `button|标签|命令`（2 列，最多 ~24 按钮）
│   ├─ ★ 限制：标签 ≤6 全角字符、装饰横线会被挤掉、不能显示图片、点击即 quit_app
│   └─ ★ 退出就回到系统 UI（它是"覆盖层"，不是"嵌入"）
│
└─ 我们的 mod 能力（两栖）
    ├─ 无 UI：prefman / capdtm / st app / EV_*.sh 直接调用  ← ★ 这才是"系统级"
    └─ 有 UI：mod_gui 菜单                          ← 只是给这些能力套个选择器
```

⇒ ★★★ **关键洞察：mod 能力本身大部分【不需要 UI】。**
`prefman set`、`capdtm setusr`、`lutload.arm import` 全是**命令行调用**。
mod_gui 只是"让人不用背命令"的选择器。

## 2. ★ `loadgui.sh` 暴露的重要事实（之前没注意）

```bash
# EV_EV.sh（机身 EV 键两次触发）
[[ $(st cap capdtm getusr MONITOROUT) | grep LCD) > "" ]] || {
    $(st app bb lcd on; st app disp lcd) && sleep 1 ; } &
killall -q mod_gui
nice -n -15 /opt/usr/nx-ks/loadgui.sh &
killall -q popup_entry & killall -q popup_ok & killall -q focus_stack & ...
```
```bash
# loadgui.sh
prefman get 0 0x0000a690 b              # ★ 直接读写 prefman
[[ "$to" = "0" ]] && prefman set 0 0x0000a690 b 1
dm=$(st cap capdtm getusr DIALMODE)      # ★ 读系统旋钮状态
case "$dm" in
  DIALMODE_SMARTAUTO) st app mode auto ;;
  DIALMODE_APERTURE)  st app mode a    ;;
  ...
esac
nice -n +15 mod_gui gui_ini &  nice -n +19 br_menu.sh &
```

⇒ ★★★ 三条推论：
1. **`st app` 是官方 CLI，可直接驱动系统 UI**（切拍摄模式、开 LCD）
2. **社区脚本已经在改系统 UI 的行为**（`prefman set 0x a690`改的是 UI 布局状态）
3. ★ **mod_gui 起来后甚至会接管拍摄模式选择**（那段 `st app mode`）⇒ 它已经"半系统级"了

## 3. ★★ 那"系统级集成"到底能不能做？分三层看

### 层 1：系统键钩子（★ 已在用，成本最低）
`EV_OK.sh` / `EV_S1.sh` 等被系统调起 ⇒ **改这些脚本 = 功能出现在系统 UI 的流程里**。
- 零风险、无需重编
- ★ 我们已用：`EV_FLAB.sh` 挂 S1 换配方
- ★ **这是真正的"系统级"，但只有按键，没有列表**

### 层 2：prefman / capdtm 改系统状态（★ 已在用）
改 `APPPREF_*` 字段让**系统自己的 UI** 显示新状态。
- ★ 已被验证：`APPPREF_WB_TYPE @0xa390`、`APPPREF_WB_K_VALUE @0xa394`
- ★ **这才是"集成进系统 UI"的正统做法** —— 不画自己的界面，改系统 UI 的数据源
- ⚠️ 限制：受限于系统暴露的字段（672 条命名表里的 app 段）

### 层 3：改 di-camera-app 本体（★★ 高成本，最后手段）
真正把功能做进原生菜单，需要改 ELF。
- ❌ **无源码**（只有 p7 与 GPL 包里的内核/中间件）
- ⚠️ 可行手段：`poker`（改 `.data`，CPU 无 NX）——但**只能改变量，不能插入代码**
- ⇒ ★ **想加"新菜单项 + 新页面"必须重编或大改 di-camera-app = 极高成本**

## 4. ★★★ 我的建议：双通道架构（不是替代）

```
┌─ 【主通道】系统级：零 UI，靠机身键直接触发
│   S1 短按  = 换下一个配方（FilmLab cycle，零延迟，实机已通）
│   S1 长按★不可得 ⇒ 改用 AEL 或 EV 键做"反向"
│   ★ 目标：99% 的操作用 1 次按键完成，不需要菜单
│
├─ 【辅通道】系统级数据源：改 prefman，让系统 UI 自己显示
│   ★ 配方切换后写 prefman ⇒ 系统 UI 的图标/参数跟着变
│   ★ 这一步还没做，是"看起来像原生"的关键
│
└─ 【调试/兜底】mod_gui：保留，但降级定位
   ★ 只在需要【选择】时用（换 LUT 名字、刷固件、看诊断）
   ★ 不再承担"日常操作"
```

### ★ 为什么这是对的
| 维度 | 全部走 mod_gui | 双通道 |
|---|---|---|
| 开机即可用 | ❌ 需按键唤起 | ★ **是**（EV_*.sh 已被系统调起）|
| 日常操作步数 | 唤起 → 找到 → 确认 | ★ **1 次按键** |
| 状态可见性 | 自己的界面 | ★ **系统 UI 自己显示**（改 prefman）|
| 出问题时的兜底 | ❌ 同一套东西坏了就全废 | ★ **两条独立通道** |
| 刷固件等高危操作 | 混在日常菜单里 | ★ 隔离在独立页 + 门控 |

⇒ ★★ **mod_gui 该留，但它的定位是"调试与高危操作入口"，不是"mod 的主界面"。**

## 5. ★★ 三个必须正视的障碍（别以为系统级集成是免费的）

### 障碍 1：★ "系统 UI 显示"改不了，因为 UI 是 p7 画的
系统菜单/图标由 **p7（ISP 固件）** 渲染，不在 Linux 侧。
- 我们改 `prefman` ⇒ 系统 UI **确实会变**（`WB_KELVIN` 已验证进 `iqr`）
- 但**新增一个菜单项**要在 p7 里加渲染逻辑 ⇒ ★ **又回到改 p7**
⇒ ⚠️ 这是"系统级集成"最容易被低估的地方。

### 障碍 2：★ 改 prefman 会被 UI 覆盖
已实测：`iqr[111] APP_MODE=3 eAPPMODE_Av` 模式系统在跑，改 pref 会被 UI 回写。
⇒ ★ **必须配合机身操作**（先在 UI 里切到对应模式），不是纯脚本能搞定。

### 障碍 3：★ 交互能力被内核吃掉
**长按/连击/组合键架构性不可得**（内核先消费 + ISP 优先）。
⇒ ★★ **系统级集成的上限 = "一次按键 = 一个动作"。**
　 任何需要"进入列表→选择"的交互，**只能靠界面**，而界面就是 mod_gui。
⇒ ★★ **这是 mod_gui 无法被完全替代的根本原因。**

## 6. ★ 那"魔灯级别"的尝试该怎么做

我的建议：**魔灯恰恰是最不需要 UI 的功能**，应该做成"按键直触"。

| 设想 | 适合系统级直触？ |
|---|---|
| ★ 换 LUT（按一次 = 下一个） | ★★ **完美适配**，本菜单根本不用 |
| ★ 4 档内置色彩循环 | ★★ 完美适配 |
| 选特定 LUT（从 20 个里挑）| ✘ 需要列表 ⇒ 用 mod_gui 或轮轮（架构不可得）|
| 导入 LUT（要挑文件）| ✘ 需列表 + 文件浏览器 |

⇒ ★★★ **所以"魔灯"的系统级形态应该是：**
1. **按键一次 = 下一个 LUT**（配合 OSD 提示当前是哪个 —— `popup_timeout` 现成可用）
2. **mod_gui 只用来"建库/导入/删除"**，不用于日常切换
3. **prefman 记录当前 LUT 名** ⇒ 重开机后恢复

⇒ ★ 这才是"集成进系统级"的正确形态：**不是把菜单画进系统 UI，而是让功能变成一次按键。**

## 7. 结论与下一步（待你拍板）

### ★ 我的结论
| 结论 | 理由 |
|---|---|
| **mod_gui 不该放弃，但该降级** | 它是唯一已验证的交互载体；且"选列表"这类需求无法被按键替代 |
| ★★ **"集成进系统 UI"应该重新理解为"变成一次按键"** | 而不是"把菜单画进原生菜单"（那需要改 p7 渲染逻辑，成本极高）|
| ★ **优先做"改 prefman 让系统 UI 显示状态"** | 这是正统系统级做法，零风险，已验证通路 |
| ★ 系统级集成的天花板 = 一次按键一个动作 | 内核吃掉长按/连击/组合键 |

### ★ 建议的下一步（三选一，取决于你想验证什么）
| 选项 | 内容 | 验证什么 |
|---|---|---|
| **A** | ★ **把 LUT 切换绑到 S1/AEL 键**（`EV_S1.sh` 加一行）| ★ 验证"零 UI 日常操作"这条路 —— **最快、成本最低、收益最直接** |
| **B** | 配方切换后**写 prefman**，看系统 UI 有没有跟着变 | ★ 系统级集成的"可见性"上限 |
| **C** | 逆向 p7 的菜单渲染逻辑，评估"真把入口画进原生菜单"的成本 | ★ 决定这条路到底值不值得走 |

⇒ ★★★ **我的建议是 A**。理由：它立刻能回答"魔灯能不能做到 1 次按键换 LUT"，
而这个答案直接决定后面 C 要不要做。
