## 一、结论先行

**★ SMA 共享区基址 `0x94000000` 确实存在于 ISP 固件里** ——
位于镜像偏移 `0x9FC0` 的一张**内存段配置表**中，与实测的 `/dev/d5_sma`
（144MB @ `0x94000000`）**完全一致**。

⇒ **这补上了昨晚留下的最后一个可能性**：
EP 与 ISP 固件**寄存器地址空间不重叠**（22:00 已证），
但**共享同一块共享内存** ⇒ 两者**通过 SMA 交换数据**。

⚠️ **但"共享内存存在"≠"数据流已确认"。** 还需确认谁写、谁读。

## 三、★★★ 确凿证据：0x9FC0 的内存段配置表

### 3.1 表的上下文（有 ASCII 佐证）

`0x9F00` 附近是 ASCII 数据：

```
0x9f00:  "SKST"          ← 标识
0x9f04:  "0215"          ← 版本？
0x9f0c:  "0123"  "456789"  "89ABCDEF"  "GHIJKLMN"  "OPQRSTUV"  "WXYZ"
0x9f40:  0x00020000  0x00000001  0x001c0089  ...
```

★ **紧邻这张表之后（`0x9F40`–`0xA050`）就是内存段配置**。
`0123…WXYZ` 是标准的 16 进制字符表（用于格式化输出），说明这片是**配置/数据区**。

### 3.2 表项结构（每条 8–16 字节）

```
0x09f80:  80000000  00000000  00000000  86000000
0x09f90:  93ffffff  00000000  00000000  0000000a
0x09fa0:  02000000  02100000  00000010  00010416     ← 0x02100000 = 2^20+0x1000
0x09fb0:  06000000  21000000  00000010  00010416
0x09fc0:  94000000  bfffffff  00000004  00001402     ★★★ SMA 基址
0x09fd0:  81000000  83800000  00000004  0000140e
0x09fe0:  83800000  84000000  00000004  00001402
0x09ff0:  84000000  86000000  00000004  00001402
0x0a000:  80000000  81000000  00000002  0000940e
0x0a010:  80000000  80011000  00001000  00000000
0x0a020:  80011000  81000000  00010000  00000000
0x0a030:  81006000  83800000  00002000  00000000
```

`0x94000000` 与 `0x80000000`（物理/共享段起点）、`0x80011000`、`0x83800000`
等**并列出现** ⇒ 它们是**同一张表里的不同内存段条目**。

### 3.3 关于 `0xbfffffff`（与 `0x94000000` 配对的那个）

| 解读 | 验算 | 判定 |
|---|---|---|
| 段长掩码 | `0xbfffffff` 高 30 位全 1 ⇒ 段长 = `0xC0000000` = 3 GB | ✘ 远超实测的 144MB |
| 段末地址 | `0x94000000` + 144MB = `0x94900000` | ✘ 远小于 `0xbfffffff` |
| **另一段的基址** | 与前后条目模式一致（都是 `基址, X, count, type`）| ✔ **最可能** |

⇒ 记作 `{段基址 0x94000000, 另一配置 0xbfffffff, count=4, type=0x1402}`。
⚠️ **未验证**，需反汇编引用代码确认字段语义。

## 四、★ 顺带解出编码规律：`0x14xx` / `0x94xx`

表里反复出现的小整数：`0x1402`(3次) `0x140e`(1次) `0x940e`(1次) `0x0004`(4次)。

高 12 位拆分（`0x1402` = 0x14 | 0x02）：

| 值 | 拆分 | 推测 |
|---|---|---|
| `0x1402` | 节点 `0x14` + 子 `0x02` | 硬件配置域 |
| `0x140e` | 节点 `0x14` + 子 `0x0e` | 硬件配置域 |
| **`0x940e`** | **节点 `0x94` + 子 `0x0e`** | ★ **与 `0x94000000` 同前缀 `0x94`** |
| `0x0004` | — | 计数（4 项） |

⇒ **推测**：`0x94xx` 是 **SMA/共享内存管理域**的节点 ID，
`0x14xx` 是硬件配置域。
⚠️ **纯推测，未验证。** 需要反汇编引用代码 + 对照 `d5_sma` ioctl 号确认。

## 五、★★★ 现在可以回答那个悬案了

### 22:00 留下的三个可能性，现在的状态

| 可能性 | 状态 | 依据 |
|---|---|---|
| EP 由 ISP 固件**直接操作寄存器** | ⛔ **已排除** | `0x0806-0x0807` 零对齐引用、零 LDR-literal；EP 地址 `0x20821c00`/`0x2082b000`/`0x80506864` 在固件里全部零出现 |
| EP 与 ISP 固件**经共享内存协作** | ✅ **正面证实** | ★ `0x94000000` 在 `0x9FC0` 的内存段表中，与 `/dev/d5_sma` 实测一致 |
| 完全无协作 | ❌ **已排除** | 同上 |

⇒ ★★★ **最终图景**：

```
┌──────────────┐   共享内存 0x94000000 (144MB)   ┌──────────────┐
│  ISP 固件     │ ◄════════════════════════════► │  EP 硬件      │
│  (ARM 模式 A32) │    帧数据 / 参数              │  (/dev/drime5_ep)│
│  p7 @ mmcblk0p7│                                │  3DLUT/NOG/MC │
└──────────────┘                                 └──────────────┘
       │                                                  ▲
       │ IPCC / 私有 IPC                                   │ ioctl + mmap
       ▼                                                  │ (Linux 用户态 UDD)
┌──────────────────────────────────────────────────────────┴──────────┐
│                    Linux (Cortex-A9) / Tizen                          │
│                    libudd5.so  ← di-camera-app                       │
└─────────────────────────────────────────────────────────────────────┘
```

**这不是"谁驱动谁"，是两个独立硬件通过共享内存协作。**
与所有实测一致：EP 走标准 UDD、`d5_ipcc` 在 Linux 侧是空壳、
ISP 固件由 bootloader 预加载。

## 六、⚠️ 仍未验证的（不夸大结论）

1. **`0xbfffffff` 的字段语义** —— 只知"与 `0x94000000` 同一条记录"。
2. **`0x14xx` / `0x94xx` 编码含义** —— 纯推测。
3. **★ 数据流方向未定** —— 共享内存存在，但**谁往里写帧、谁读**没验证。
   可能是：ISP 写 → EP 读（ISP 是生产者）
   或：EP 写 → 显示/JPEG 读，或双向乒乓。**这是下一步的重点。**
4. **表的引用代码未找到** —— `0x9F40`–`0xA050` 无 LDR/ADD 直接引用，
   说明表基址通过**寄存器间接寻址**（先加载到某寄存器，后续偏移索引），
   标准 PC-relative 扫描找不到。**需要更强的数据流分析。**
