## 1. ★★★ 决定性工具：`dump`（从硬件读回）

### 1.1 为什么需要它
之前所有格式判断都靠"从 p7 反汇编 + 从出厂缓冲猜"⇒ 反复出错。
**读回硬件是唯一能拿到真值的手段。**

### 1.2 逆向依据（libudd5）
```
sub_3a888 (写) 末尾 = SelLUT(sel); rw_Start(1)   ← 1 = 写方向
sub_3a9e0 (读) 末尾 = SelLUT(sel); rw_Start(2)   ← ★ 2 = 读方向
```
两者结构**完全对称**，只差 `rw_Start` 参数 ⇒ **硬件支持读回**。

### 1.3 实现
```c
b[R_ONOFF/4] |= 1;      /* OnOff(1) */
b[R_PULSE/4] &= ~1;     /* Acc(0)  */
b[R_PULSE/4] |= 1;      /* Acc(1)  */
SelLUT(sel);            /* bits[5:4] */
b[R_LUT0/4] = phys;     /* ★ 读回目标 = 我的 CMA */
rw_Start(2);            /* ★ bit4 = 读方向 */
```

## 2. ★★★ 签名表实验 —— 一次性确定 DMA 语义

### 2.1 实验设计
生成一张**每个字节都不同**的伪随机表（9248 字节），写入后再dump 回来比对。
出厂表是灰阶，dump 出来也是灰阶 ⇒ **无法区分"真读回"和"读到伪数据"** ⇒ 必须用签名表。

### 2.2 结果 —— 一字不差
```
写入: sig9248.bin 9248 字节
读回: dump_sig.bin  16384 字节
★ 签名表前 64 字节在读回中的位置: 0
★ 完整 9248 字节一致? YES ★★★
```
逐字节对比：
```
读回  +00: 00 00 b1 79 62 f3 13 6d c4 e6 75 60 26 da d7 53
写入  +00: 00 00 b1 79 62 f3 13 6d c4 e6 75 60 26 da d7 53   ← 完全一致
```

### 2.3 ★★★ 由此同时确定了三件事
| 结论 | 依据 |
|---|---|
| ★ **DMA 双向通** | 写进去能原样读回来 |
| ★★ **搬运长度 = 提供的字节数** | 给 9248 就搬 9248，零填充也是 9248 |
| ★★ **硬件不转换格式** | 读回字节 = 写入字节，无任何重排/量化 |

⇒ ★★★ **这条推论极其重要**：既然硬件原样搬运、长度由我决定，
　那么"花屏"**不可能是格式解释错**（硬件根本不看格式），
　**只可能是"我给的表不是硬件期望的那张表"**。

## 3. ★★★ 出厂表的真实结构

### 3.1 dump 出来的数据特征
```
首个非零偏移 : 578 (0x242)
连续非零长度 : 9248 字节
其后          : 零散、无周期（DMA 尾噪，不是表的第二部分）
```
四个通道 `SelLUT(0/1/2/3)` 读回的 64 KB **完全相同（0 字节差异）**
⇒ ★ **一次 dump 只读到一张表**，`SelLUT` 在读方向的语义与写方向不同。

### 3.2 逐组分析（结构完全整除）
按 289个值（= 17×17）分组，每组**单一值**：

| 组 | 值 | 十进制 | 归一化 |
|---|---|---|---|
| 0 | `0x0fff` | 4095 | 1/16 = 0.0625 |
| 1 | `0x1fff` | 8191 | 2/16 = 0.1250 |
| 2 | `0x2fff` | 12287 | 3/16 = 0.1875 |
| … | … | … | … |
| 15 | `0xffff` | 65535 | 16/16 = 1.0000 |

### 3.3 ★★★ 定案
```
9248 字节 = 4624 个 u16(LE) = 16 组 × 289 个(17×17)
每组单一值 = (g+1) × 0x0fff
```
⇒ ★★★ **这是【16 级量化 × 17×17 网格】的灰阶表**，
　　 不是此前猜的"17 级三维 LUT"。

★ 值域规律：`(g+1) × 0x0fff` 而非 `round((g+1)/16 × 65535)`
　⇒ 说明**输出量化步长 = 4096**，即硬件内部按 12 位有效位工作。

## 4. ★★★ 花屏根因：三张图的严格解读

| # | 写入内容 | 字节数 | 画面 | 说明 |
|---|---|---|---|---|
| 1 | identity（8-bit 单通道）| 4913 | **纯绿噪点** | 只填了表的~53%，几乎全错 |
| 2 | 出厂表内容（16 级灰阶）| 9248 | **淡紫偏色 + 有结构** | 填满 1 张表，另 2 张还是旧内容⇒ 混合偏色 |
| 3 | ★ **半按快门对焦** | — | ★★★ **色彩完全正常** | p7 重新搬运出厂表⇒ 覆盖污染 |

### 4.1 ★★★ 为什么"半按对焦"能恢复（这是最关键的一步）
```
AF（对焦）流程 → p7 重新调用 FUN_0009a3e8 取 LUT 地址
              → SetAddress + rw_Start(1)
              ⇒ DMA 重新搬运【出厂表】⇒ 把我污染的内容覆盖掉
```
⇒ ★★★ 这解释了此前**每一次**"半按快门就恢复"的现象。
⇒ ★★ **`restore` 只改指针（+0x00c），不改表内容 ⇒ 单靠 restore 无法修复**，
　　 必须触发一次 ISP 重载（即半按对焦）或写入正确内容。

### 4.2 ★★ 三通道总量
| 张数 | 字节 |
|---|---|
| 1 张 | 9248 |
| 2 张 | 18496 |
| ★★ **3 张（R/G/B）** | ★★ **27744** |
| 4 张 | 36992 |

⇒ ★★★ **我始终只写了 1 张表 ⇒ 另外 2 张残留着上次的内容或初始状态
　　 ⇒ 混色 ⇒ 偏色。** 这就是花屏的全部原因。

## 5. ★★★ 格式定案（最终）

```
┌─ 3D LUT 数据结构 ────────────────────────────────────┐
│  3 张独立表（R / G / B），每张 9248 字节│
│  每张 = 16 组 × 289 个 u16(LE)│
│  289 = 17 × 17（输入网格）│
│  每组 289 个值全相同（该组的输出）│
│  值 = (g+1) × 0x0fff（16 级量化，步长 4096）│
│  总计 = 27744 字节│
└────────────────────────────────────────────────┘
```

| 项 | 值 |
|---|---|
| ★ 通道数 | **3（R/G/B 各一张）** |
| ★ 每通道字节 | **9248** |
| ★ 总字节 | **27744** |
| ★ 元素类型 | **u16 LE（16-bit）** |
| ★ 网格 | **17 × 17 = 289** |
| ★ 级数 | **16**（量化步长 4096） |
| ★ 输出公式 | `(g+1) × 4095`（出厂灰阶）|

⚠️ **尚未 100% 确认**：`17×17` 网格的**两个维度分别对应哪个输入通道**
（色彩空间 Cb/Cr？还是 R/G？）。这需要三通道分别 dump 后对比。

# ★ §11 【自查推翻】2026-10-06 18:25

## 11.1 触发事件

用户实机反馈：**执行"恢复出厂"后画面变成淡紫偏色，半按快门对焦才恢复正常。**

★★★ 这直接推翻了 §9"安全记录"里那句"每次实验后 restore ⇒ 零风险"。
⇒ **restore 不是无害的，它本身是bug。**

## 11.2 ★ 根因：restore 走完整写入序列，无条件触发 DMA

复查 `do_write_seq()` 代码：

```c
/* ---- 步骤 11：rw_Start(1) —— 发起硬件 DMA 搬运 ---- */
v = b[R_PULSE / 4];
v |= 0x100UL;
b[R_PULSE / 4] = v;
v &= ~0x100UL;
b[R_PULSE / 4] = v;          ← ★★★ 无条件执行，没有开关
```

而 `restore` 调用的是同一个 `do_write_seq(b, FACTORY, 0, 0)`。

⇒ ★★★ **所以"恢复出厂"实际做的是**：
1. `+0x00c` ← `0x81115200`
2. ★ **再把 `0x81115200` 的内容 DMA 灌进硬件一次**

## 11.3 ★★ 为什么第二次灌入是有害的

p7 的正确流程是：

```
FUN_0009a3e8()              ← 【先准备数据】从 4 个常量里选一个
       ↓ 返回物理地址
FUN_004dbb08(..., 0xb4, ...) ← 通知 ISP
       ↓
FUN_00179314(addr, ...)      ← 再 SetAddress + rw_Start(1) 灌入
```

⇒ ★★ **`0x81115200` 指向的缓冲，其内容是由 p7 在 `FUN_0009a3e8` 里选出来的源。**
⇒ ★★★ **我在没有跑 prepare 的情况下直接灌它**，
     等于把**过期或未初始化的内容**灌进硬件。

⇒ ⇒★ **这解释了为什么寄存器回读完全正确、画面却依然偏色。**
⇒ ★★ **寄存器值 ≠ 硬件实际生效的数据。**（铁律的又一条实例）

## 11.4 ★★★ 我犯的方法论错误（比技术错误更重要）

| 我写的结论 | 实际只能推出|
|---|---|
| "DMA 搬运长度 = 我给的字节数（签名表验证一字不差）⇒ 表长 = 9248" | ★ **搬运长度由我定 ≠ 硬件期望的表长** |
| "dump 出 9248 字节灰阶 ⇒ 16 级 × 17×17" | ★ **我只 dump 到 9248 字节，因为我只读了这么多** |
| "淡紫偏色有结构 ⇒ 1/3 表正确、2/3 垃圾" | ★ 更可能是**整表都是垃圾**，只是垃圾非全零所以还能看出图像结构 |

⇒★★★★★ **我把「DMA 的搬运机制」当成了「LUT 的格式」。**
⇒ 这是典型的：**用一个只能证明 A 的实验，去证明 A 和 B。**

### ★★ 缺失的那个实验
**应该做**：先让 p7 灌一次（半按快门），**立刻 dump**，
⇒ 此时读回的长度才是**硬件真实的表长**。
⇒ ★ 我是先 dump（未 prepare 状态）就下了格式结论。

## 11.5 ★★ 已修复：safe_restore

新增 `safe_restore()`，**只改指针，绝不触发 DMA**：

```c
static void safe_restore(volatile unsigned *b)
{
    b[R_LUT0 / 4] = FACTORY;        /* 指针指回出厂表 */
    b[R_LUT1 / 4] = FACTORY;
    v = b[R_CFG / 4];  v &= ~0x1333UL;  b[R_CFG / 4] = v;   /* 通道/格式交回 p7 */
    v = b[R_PULSE / 4]; v &= ~0x110UL;  b[R_PULSE / 4] = v; /* ★ 不置bit8/bit4 =不触发 DMA */
    /* 然后提示用户半按快门，让 p7 自己灌 */
}
```

★ `preset` 命令也改成同样逻辑（只改指针，不主动 DMA）。

## 12.1 正确的实验顺序（§11 缺失的那一步）

```
① 先让 p7 灌一次表（★ 半按快门对焦）⇒ 进入"已 prepare"状态
② 立刻 dump ⇒ 读回硬件【实际生效】的表
③ 写入一张 4913 个 u16 的伪随机签名表，立刻再 dump
④ 比对：读回与写入【一字不差】，最大连续段恰为 9826 字节
```

⇒★★★★★ **§11 的错误根源**：我在"未prepare"状态下 dump，
　测到的是过期数据，却拿它下了格式结论。

## 12.2 ★★★ 决定性证据一：prepare 前后数据不同

| 状态 | 主段位置 | 主段长度 | 非零总数 |
|---|---|---|---|
| 未 prepare（§4 那次）| 0x00242 .. 0x02662 | 9248 | 10469 |
| ★★ **prepare 后（本次）** | ★★ **0x00000 .. 0x02662** | ★★ **9826** | ★★ **11111** |

⇒ ★★ **主段起点归零、长度从 9248 变成 9826。**
⇒ 这直接证明：**未 prepare 时读到的确实不是有效表。**

## 12.3 ★★★ 决定性证据二：签名表实验（排除读回伪影）

```
写入 sig4913.bin：4913 个 u16 = 9826 字节，伪随机
读回最大连续段   ：0x00000..0x02662 = 9826 字节
逐字节比对       ：★ 一字不差
```

⇒ ★★★ 这一条同时排除三种可能：
| 被排除的解释 | 理由 |
|---|---|
| "读回有伪影/高位丢失" | 签名表低 12 位**不是**全1，仍一字不差读回 |
| "DMA 会做格式转换" | 伪随机值原样回来 |
| "表长不是 9826" | 连续段**恰好** 9826 字节，多一字节不少 |

## 12.4★★★★ 最终格式（定案）

```
┌─ NXKS 3D LUT 数据结构 ────────────────────────────┐
│ 级数= 17（每维17 个节点）                │
│ 维度    = 17 × 17 × 17                          │
│ 总节点  = 17³ = 4913★ 不是 4913×3│
│ 元素    = u16 LE（16-bit）│
│ 总字节  = 9826                │
│ 每节点  = ★1 个 u16（标量表，不是 R/G/B 三元组）│
│ 分组    = 每 289 个（=17×17）为一组，共 17 组       │
│ 顺序    = 最外层维度变化最慢（ri）│
└───────────────────────────────────────────────┘
```

### 出厂灰阶表内容（实测对照基准）
| 组 g | 值 | 十进制 |
|---|---|---|
| 0 | `0x0fff` | 4095 |
| 1 | `0x1fff` | 8191 |
| … | … | … |
| 15 | `0xffff` | 65535 |
| 16 | `0xffff` | 65535（饱和） |

⇒ 值 = `(g+1) × 0x0fff`（16 级量化步长 4096）
⇒ **输入索引 17 级，输出有效量化 16 级**

### ★★ 与标准 3D LUT 的关键差异
| 项 | 标准 .cube 3D LUT | ★ NXKS 实测 |
|---|---|---|
| 每节点值数 | 3（R,G,B）| ★ **1（标量）** |
| 总字节（17 级）| 29478 | ★ **9826** |
| 通道表达 | 表内交织 | ★★ **多张表 + `SelCbCr_ch` 选择** |

⇒ ★★ **所以 .cube 的 RGB 输出必须先压缩成标量**（当前用亮度加权）
⇒ ⇒ ★ **这可能正是此前花屏的深层原因之一**：我一直喂 RGB 三元组，
　而硬件每节点只要 1 个标量。
