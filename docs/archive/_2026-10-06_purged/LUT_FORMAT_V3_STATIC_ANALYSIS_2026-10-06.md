## 一、★★★ 格式定案：从指针间距算出来的唯一解

### 决定性事实
p7 的 `.data` 段里有 **28 个 LUT 数据指针**，全部静态初值、全部只读：

| 组 | 数量 | 位置（文件偏移） |
|---|---|---|
| 静态 4 档 | 4 | `0x3837f0` ~ `0x3837fc` |
| 动态 24 档 | 24 | `0x383a24` ~ `0x383a80` |

### ★★★ 关键观察：指针间距精确等值
把 24 个动态指针排序后，**相邻间距几乎全部等于 `0x4D00` = 19712 字节**（256 字节对齐）：
```
0x810c3500 → 0x810c8200 = 0x4D00
0x810c8200 → 0x810ccf00 = 0x4D00
...（23 处全部 0x4D00，唯一例外 0x810f8400→0x81123d00 = 0x2b900，是空洞）
```
4 个静态指针的间距同样是 `0x4D00`（第 3→4 档为 `0xE700`，含空洞）。

### ★★★ 求解：唯一解 = 17³ × 4 字节
| 节点数 N | 每节点 BW | N×BW | 对齐到 256 | = 19712？ |
|---|---|---|---|---|
| 4913 = 17³ | **4** | **19652** | **19712** | ★★★ **唯一吻合** |
| 4913 | 2 | 9826 | 9984 | ✘ |
| 4913 | 6 | 29478 | 29696 | ✘（超槽位）|
| 4914 | 4 | 19656 | 19712 | （非立方数，舍）|
| 33³ | 4 | 143748 | 143872 | ✘ |

⇒ ★★★ **格式 = 17 × 17 × 17 = 4913 节点 × 4 字节/节点 = 19652 字节**（分配槽 19712，256 对齐）

### ★★ 这直接排除了「RGB 三通道 u16 交织」
```
29478 字节（17³ × 3 × u16）> 19712 ⇒ ★★ 永远装不下 ⇒ 不可能是三通道交织
```
⇒ ★★★ **每节点 4 字节 = 1 个 32-bit 值 / 2×u16 / 或 4×u8**
⇒ ★★★ **我 10-06 下午的「16-bit 三通道」判断是错的；中间「标量 u16」也错。正确是 4 字节/节点。**

## 十、★★★★★★ 根因确认：View 不等 DMA 完成（静态已闭环）

### ★★★ View::_run 的第二步是什么
```asm
0x8011e3c0: mov  r0, #4
0x8011e3c4: bl   0x80524664      ← ★★★ 调度器的「让出/等待」函数
```
`FUN_00524664` 开头：
```asm

b<跳走>             ; 若非 0 → 不等，直接返回
```
⇒ ★★★ **它就是「等 DMA 完成」的挂起调用**（参数 0 = 不等待）。
⇒ ★★★ **View::_run 调它时传的是 `r0=4` ⇒ 走「不等」的分支！**

### ⇒⇒★ 完整因果链（静态闭环，无需再实验）
```
View::_run(0x11e3b4)
  ├ mov r4,#0                ← 第 3 参数 = 0（Still 传真值）
  ├ bl 0x11e380 (共用主体 _setCtrl)
  └ mov r0,#4 ; bl 0x80524664 ← ★ 传 4 ⇒ 「不等」分支 ⇒ 立刻返回

⇒⇒★★★ DMA 还在搬运时，取景器就开始读表 ⇒ 读到半成品 ⇒ 粉绿花屏
⇒⇒★★★ 而 Still 走 _run 时等到了 load Done ⇒ 照片正常
```

⇒ ★★ **方案 A 最安全**：我 `poke` 写完表后**多等一会儿**再触发，

## 十二、★★★★★★★★★ 【最终定案】View 与 Still 的真实差异（capstone 精确反汇编）

### ★★★ 纠正前一轮的错误
之前我手写十六进制解码，**把数据当代码读了**。
⇒ ★★ "View 不等 DMA" **结论作废**。用 capstone 重读后真相完全不同。

### ★★★★ 三个类的虚表（+0x14 = `_load`，+0x18 = `_run`）
| 槽 | **View** | **Still** | **CS** |
|---|---|---|---|
| vtable | `0x805837f8` | `0x805838a0` | `0x8058397c` |
| +0x14 | ★ `0x11e20c`（83 条） | `0x11e7b8`（11 条）| `0x11ed80` |
| +0x18 | `0x11e3b4`（6 条）| `0x11e7ec` | `0x11edf0` |

### ★★★ `View::_run` 真相= 【对象构造器】
```asm
push {r4, lr}
mov  r4, r0
bl   #0x8011e380      ; ★★ 构造一个新 3DLUT 对象（写 vtable + 调Base::_init）
mov  r0, r4
bl   #0x80524664      ; ★ 收尾钩子（cmp r0,#0; blne → veneer 区）
mov  r0, r4
pop  {r4, pc}
```
⇒ ★★★ **`_run` 完全不搬 LUT 数据**（我上一轮说它"不等 DMA"是错的）

### ★★★★★★ 真正的差异：`View::_load` 83 条指令里有【两条灌入路径】
```asm
cmp  r1, #0x10000002        ; ★★ 消息类型
beq  #0x8011e2e8            ; ★★ 走这条 → 完全不同的分支
  ; --- 路径 A（正常）---
  ldrb r7,[r0,#0x20] / r4,[r0,#0x21] / r6,[r0,#0x22]   ; 三个选择字节
  bl   #0x800f6474           ; 加载 DataPocket
  bl   #0x8009a3e8 / #0x8009a408    ; ★ 静态 4 档 / 动态 24 档选表
  bl   #0x804dbb08           ; 通知 ISP (0xb4)
  mov  r0, r4                ; 表地址
  mov  r2, r5                ; ★ r5 = (byte_at(+0x40) != 1)
  bl   #0x80179314           ; ★★ LoadLut(addr, 0, r5, 0)

  ; --- 路径 B（0x10000002）---
  ldrb r0, [r0, #0x24]
  bl   #0x80176884           ; ★★★ 完全不同的 API
  bl   #0x80175c80
```

### ★★★★★★ `FUN_00176884` = 【18路跳转表】，★ 它不处理 3D LUT
```asm
sub  r0, r0, #1
cmp  r0, #0x11               ; ★★ 17+1 = 18 项
ldrls pc, [pc, r0, lsl #2]  ; ★★ 跳转表
```
18 个 case 里只有 **8 个独立**，其余全落默认分支`0x80176b84`：
| case | 目标 | 内容 |
|---|---|---|
| **0** | `0x80176b8c` | `str #1, [sp,#0x44]`（★ 长度 **1**）|
| **1** | `0x80176bb8` | `str #2, [sp,#0x44]` + `mov r2,#0x8b` + `bl 0x800465bc`（★ **139 字节文件**）|
| 6 | `0x80176c08` | 独立 |
| 10 / 14 / 15 / 16 | — | 独立 |
| 17 | `0x801768fc` | =下一条指令（继续主流程）|
| 其余 9 个 | `0x80176b84` | ★ 默认/错误 |

⇒ ⇒★★★ **这条路径处理的是【材质描述 / 元数据】，不是 3D LUT 表。**
⇒ ⇒★★ **`+0x24` 是 8 种材质预设索引**（`STILL_3DLUT_NORMAL/CS/SELECT_COLOR`…）
