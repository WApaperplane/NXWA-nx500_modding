# 3D LUT 实机写入实验 — 全记录
---
> ## ⚠️⚠️⚠️ 2026-06 晚·结论纠正声明（必读）
>
> **本文档中「导入 LUT 内容必须改 P7」这一结论已被推翻。**
>
> 当时把 `d5_ep_3dl_load_lut` 误当成"挂地址"（往 `+0x0c` 写一个地址让硬件自己去读）。
> 复核后确认它走的是 **WDMA 硬件 DMA**：数据放在**调用者自己的 CMA 缓冲**（`/dev/d5_sma`），
> 由硬件 DMA 搬进 3D LUT 内部 RAM ⇒ **完全不涉及 `0x81xxxxxx`** ⇒ **Linux 用户态可以导入任意 LUT**。
>
> | 项 | 定论 |
> |---|---|
> | 被推翻 | "LUT 数据缓冲在 p7 地址空间 ⇒ 必须改 P7" |
> | 成立 | **导入 .cube LUT：用户态可做，不需要改固件** |
> | 仍需改 P7 的唯一理由 | 要改**ISP 生成 LUT 的算法**（tone curve 能力），不是"搬数据" |
>
> 关键证据：`ConfigAccessMode → sub_3a888 @0x3a888`（静态函数，本次解开）
> → `OnOff(1)→Acc(0)→Acc(1)→SetAddress(自己的 CMA 地址)→SelLUT→rw_Start(1)`，
> 其中 `rw_Start(1)` = `+0x008 |=0x100 → &=~0x100`（write-1-clear 触发 DMA）。
> ★ 另：`+0x0c` 写固件常量地址（4 档切换）是一条**独立通路**，与导入无关。
>
> 详见 `docs/LUT_IMPORT_2026-10-06.md` 与 `.workbuddy/memory/topics/ep-3dlut.md`。

## 2. ★★★★ p7 的 3D LUT 权威寄存器定义

来源：`raw8/p7/ghidra/53_all_pseudocode.c:641680+`（内核态反编译）

| 寄存器 | 位 | 函数 | 语义 |
|---|---|---|---|
| `+0x000` | bit0 | `FUN_004cf3d4` | **OnOff 总开关** |
| `+0x004` | bits[1:0] | `FUN_004cf3fc` | SelCbCr |
| `+0x004` | bits[5:4] | `FUN_004cf414` | SelLUT 通道 |
| `+0x004` | bit8 | `FUN_004cf42c` | LUT0 数据源 |
| `+0x004` | bit12 | `FUN_004cf444` | LUT1 数据源 |
| `+0x008` | **bit0** | `FUN_004cf45c` | ★ **写启动脉冲** |
| `+0x008` | bit8 / bit4 | `FUN_004cf484` | ★ **读侧清理** |
| `+0x00c` | — | `FUN_004cf4b4` | LUT0 数据地址 |
| `+0x010` | — | `FUN_004cf4b4` | LUT1 数据地址 |

⇒ ★★★ **p7 只访问这 5 个寄存器**（`grep -oE "2082b[0-9a-f]{3}" | sort -u` 穷举确认）
⇒ 没有 bypass/process 寄存器。

### ★★★ 完整写入序列（6 步，一步都不能少）

```c
b[0x000] |= 1;              // ① FUN_004cf3d4(1)  OnOff
b[0x008] &= ~1UL;           // ② FUN_004cf45c(0)  ★ 脉冲位先清零
b[0x008] |= 1UL;            // ③ FUN_004cf45c(1)  ★ 置位启动
b[0x00c] = lut_phys;        // ④ FUN_004cf4b4     SetAddress
b[0x004] &= 0xffffffcfUL;   // ⑤ FUN_004cf414     通道选择
b[0x008] &= ~0x100UL;       // ⑥ FUN_004cf484(1)  ★★ 读侧清理
```
★ **② 和 ⑥ 是我前 5 次实验全部无效的原因。**
★ 客观判据：**执行后 `+0x008` 保持为 1 = 硬件接受了启动**（之前每次都被清零）。

### 硬约束
```c
/* FUN_00179314 */
if ((param_1 & 0xff) == 0) { ... }    /* ★ LUT 物理地址必须 256 字节对齐 */
```
⇒ 与我从 libudd5 静态解出的 `if ((phys & 0xff) != 0) return -301;` **完全对应**
⇒ **用户态反汇编 + 内核态反编译双向交叉验证成功。**

## 3. ★★★★ 实测的 16 组寄存器（每 0x100 字节重复）

```
+0x00 = 0x00000001    ← OnOff = 开
+0x04 = 0x00000100    ← bit8 = LUT0 数据源
+0x08 = 0x00000000    ← 脉冲位（写后自清）
+0x0c = 0x81115200    ← LUT0 数据地址（p7 预置）
+0xfc = 0x13020619
其余全 0
```
★ ★★ 与 p7 定义 **4/4 完全吻合**。
★ 写一组 `+0x08` 会让 **16 组同时变** ⇒ 它们是同一寄存器的 16 份视图。

## 4. ★★★★★★ 4 个预置 LUT 缓冲 = 三星内置色彩方案

```c
/* p7 .data 常量（FUN_0009a3e8 只是从这4 个里选一个返回）*/
DAT_003837f0 = 0x810fd100
DAT_003837f4 = 0x81106b00
DAT_003837f8 = 0x81115200    ★ 与实测 +0x0c 一致
DAT_003837fc = 0x81101e00
```

| 缓冲 | 前 64 字节特征 | 推测方案 |
|---|---|---|
| `0x810fd100` | `15000d00 23000c00...`（非单调）| 风格化曲线 |
| `0x81101e00` | `00000000 10000000 20000000...`（完美线性）| ★ **纯 identity** |
| `0x81106b00` | 与第1 个完全相同 | 同上 |
| `0x81115200` | `00ff0001 fe0002fd...`（R↑G↓）| ★ **暖色调/肤色** |

⇒ ★★★★★★ **「三星魔灯」的本体就是这 4 个方案**。

### LUT 数据格式（从 `0x81115200` 前 32 words 解出）
```
0100ff00  fd0200fe  00fc0300  0500fb04  f90600fa  00f80700  0900f708 ...
```
★ 小端 16-bit 拆分 ⇒ **R 通道 16 级递增（0x0001→0x00ff），G/B 同时递减**
⇒ ★★★ **17³三维 LUT 的一个 R 切片，16-bit 三通道交织**
⇒ ★★ **我之前用 8-bit RGB 是错格式** —— 这才是花屏根因。

## 5. ★★★★ 决定性障碍：那 4 个缓冲在 p7 的地址空间

| 事实 | 依据 |
|---|---|
| Linux `mem=512M` ⇒ 物理上限 `0x20000000` | `/proc/cmdline` |
| p7 页表只覆盖 `0x80000000..0x80ffffff`（1:1，16 PTE）| `50_page_table.txt` |
| `0x81xxxxxx` 超出 p7 静态页表 | ⇒ 运行时动态映射 |
| `sma_mmap` 对 `0x81115200` 返回 EINVAL | 实测（`__phys_to_pfn` 得 0）|

⇒ ★★★★ **Linux 用户态永远无法读写那 4 个 LUT 缓冲。**
⇒ ⇒★★★★★ **唯一实现路径 = 改 P7 固件**。

★ **这就是"魔灯必须改 P7"的最终证据** ——
不是"写入者在 p7"，而是"**LUT 数据缓冲本身就在 p7 的地址空间里**"。

## 6. 实验时间线

| # | 实验 | 画面 | 结论 |
|---|---|---|---|
| L1 | 只对`+0x08` 打脉冲（bit8）| — | ✔ 零副作用 |
| L2 | 写 `+0x64/68/6c/70` | — | ✔ 发现也是自清零型 |
| L3 | identity → `0x81115200` | 无变化 | 地址是p7 预置，用户态改不了 |
| L4 | `SMA_ALLOC` | — | ❌ `sma_dev==NULL` |
| L5 | `/dev/mem` 写 CMA | — | ❌ SIGSEGV |
| L6/L7 | `/dev/d5_sma` mmap CMA | 无变化 | ✔ 写入成功，但地址/格式错 |
| **L9** | 补齐 6 步（bit0 脉冲）| ★ **偏红花屏** | ★★★ **3DLUT 生效了** |
| L10 | 完整 6 步 + 压红 LUT | ★ **偏红花屏** | ✔ 复现成功 |
| L11 | 完整 6 步 + 8KB 全零 | ★ **仍花屏** | ⇒ 排除"LUT 内容"，指向格式 |

★ 全零 =identity 等价却仍花屏 ⇒ 因为格式错（8-bit vs 16-bit）。
★ **触屏/对焦后恢复** ⇒ LUT 是软状态，UI 重绘会重置，**风险等级比预想低**。

## 7. ★ 本轮修正的 7 个错误

| # | 错误 | 真相 |
|---|---|---|
| 1 | "STRICT_DEVMEM 阻塞 `/dev/mem` 写" | ❌ 内核 `# CONFIG_STRICT_DEVMEM is not set`，实测可写 |
| 2 | "CMA 区 98.6%空闲" | ❌ 采样太稀疏，`0x9a000000` 实读有数据 |
| 3 | "16 个独立 LUT 槽" | ❌ 同一寄存器的 16 份视图 |
| 4 | "脉冲是 bit8" | ❌ p7 定义是 **bit0** |
| 5 | "`+0x64/0x68` 全 0 ⇒ 硬件关闭" | ❌ OnOff 在 `+0x00`，实测 =1，**硬件是开着的** |
| 6 | "`ps\|grep` 判进程在不在" | ❌ busybox `ps` 只显示当前 pts，须用 `/proc/*/comm` |
| 7 | "写 LUT 数据就能改色彩" | ❌ **LUT 缓冲在 p7 地址空间，用户态不可达** |

⇒ ★★★★ **四次"工具失效导致的假阴性"**
（grep 零结果 / ps 零结果 / STRICT_DEVMEM 臆断 / CMA 空闲臆断）
⇒ ★★★★ **铁律：任何"零结果"都必须先自证工具有效。**

## 8. 下一步（★ 明确）

**改 p7 固件**，具体切入点已经定位：

```c
/* p7 的 0x9a3e8 附近插入"从用户态缓冲区复制 LUT 数据" */
FUN_0009a3e8() {
    ...
    return DAT_003837f4;   /* 返回其中一个预置地址 */
}
/* ★ 在这里加：把用户传入的 LUT 复制到返回的那个地址 */
```

| 步骤 | 内容 |
|---|---|
| 1 | 找到用户态 → p7 的数据传递通道（`/dev/`某节点 or IPCC）|
| 2 | 在 `FUN_0009a3e8` 后加 memcpy|
| 3 | 用 SLP 官方退路做备份（记忆：**SLP[5] 逐字节等于 p7**）|
| 4 | 刷机验证 |

⇒ ★★ **风险可控**：p7 改动只是"多复制一段数据"，不涉及硬件时序。
