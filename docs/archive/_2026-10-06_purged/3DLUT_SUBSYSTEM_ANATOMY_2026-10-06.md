### ② ★★★★★★ 灌入链路的完整真相（本日最重要发现）
```
View::_load @0x11e20c
  └ FUN_00179314(addr, 0, r5, 0)        ← 我一直逆向的这个
       ├ if (addr == 0) return -1        ← "lut base addr is NULL!"
       ├ 打包 4 参 → FUN_00173f34(单例, 0x20000003, …)   ★★ 异步入队
       └ b 0x804a5cf8 → 0x80061594 → 0x800602ac   ★★ 真正的实现
            ├ cmp arg1, #0x10400001 / #0x10400002 / #0x10400006
            └ ubfx r3, arg1, #0x10, #8 ; cmp r3, #7 → b 0x80096574
```
⇒ ⇒★★★★★ **`FUN_00179314` 不是"灌入函数"，是【请求投递器】**
⇒ ⇒★★★★★ **第 2 参不是布尔，是 `0x1040000X` 形式的【通道/格式 ID】**

### ③ ★★★★★★ "照片正常 / 取景器花屏"的结构性解释
`View::_load` 里三条字节取自**后端对象**（不是 `st3dlutParam`，那是两级间接）：
```asm
ldr  r2, [r0, #0x10]     ; 后端对象
ldrb r2, [r2, #0x40]     ; ★ byte A
ldrb r7, [r0, #0x20]     ; ★ byte B
ldrb r4, [r0, #0x21]     ; ★ byte C
ldrb r6, [r0, #0x22]     ; ★ byte D
```
⇒ ★★★ **这4 个字节决定：通道选择（+0x21/+0x22）、模式（+0x40）、同步（r5）**
⇒ ★★★ 拍照通路不经过 `View::_load` ⇒ ★★ **我改的表对拍照有效、对取景器可能缺了通道参数**

### ★★★ 第 4 层的通道 ID 分派（关键）
```asm
cmp  r4, #0x10400001 ; beq → …388     ; 通道 1
cmp  r4, #0x10400002 ; beq → …3b8     ; 通道 2
cmp  r4, #0x10400006 ; beq → …3e0     ; 通道 6
bl   0x800cbf14(未知)
ubfx r3, r4, #0x10, #8  ; ★★ 取bit[23:16]
cmp  r3, #7
bne → add r0, r6, #4  ;  ★ 用结构体 +0x04
     → b 0x80096574
beq → add r0, r6, #0x24 ; ★★ 用结构体 +0x24（另一种布局）
```
⇒ ★★★ **`bit[23:16] == 7` 时数据结构偏移从 `+0x04` 变成 `+0x24`**
⇒ ★★★ 这是本项目发现的第一处**格式切换开关**

## 十三、★★★★★★★★★ 【根因确定】拍照与取景器走两套独立的选表逻辑

### ★★★★★★★★ 完整分岔链（capstone 逐层验证，共 5 层）
```
View::_load  @0x11e20c                Still::_load @0x11e678
  cmp #0x10000002  ★ 闸门                 cmp #0x20000002  ★ 闸门
  读 +0x20/+0x21/+0x22 ★ 3 字节           读 +0x21/+0x22     ★ 只2 字节
  bl 0x8009a3e8  (View 选表)             bl 0x8009a3c8  (Still 选表)
     ↓ b 0x802b03f4                            ↓ b 0x802b03d4
  bl 0x8029b480                              bl 0x8029b480
     ↓ b 0x8029baa4                            ↓ b 0x8029ba84
  bl 0x80381a60                              bl 0x80381a60
     ↓ b 0x80381b2c                            ↓ b 0x80381abc
★★★ ★★ View 最终实现                     ★★ Still 最终实现
    @0x3837d0（7 条指令）                    @0x382b30（多参数加权）
```

### ★★★★★★★★ View 的最终实现全文（★ 这是取景器的全部逻辑）
```asm
0x803837d0: cmp      r2, #1
0x803837d4: ldreq    r3, [pc, #0x14]   → 0x3837f8 = 0x81106b00（电影）
0x803837d8: ldreq    r0, [pc, #0x14]   → 0x3837f4 = 0x81101e00（黑白）
0x803837dc: ldrne    r3, [pc, #0x14]   → 0x3837fc = 0x81115200（肤色）★← 我改的
0x803837e0: ldrne    r0, [pc, #0x14]   → 0x3837f0 = 0x810fd100（标准）
0x803837e4: cmp      r1, #1
0x803837e8: moveq    r0, r3            ; r1==1 → r3；否则 → r0
0x803837ec: bx       lr
```
⇒ ⇒★★★★★★ **取景器的 4 档选择完全由 `r1`（=`st3dlutParam.+0x22`）决定**
⇒ ⇒★★ **`0x3837d0` 紧邻 4 档指针区 `0x3837f0`（仅差 0x20）⇒ 它们是一体的**

### ★★★★★★★★ Still 的最终实现 @0x382b30（完全不同的算法）
```asm
bl 0x802b0000 / 0x802aff3c / 0x802b0078   ; ★ 三个参数（Picture Wizard 三维）
add r6,r6,r0 ; add r6,r6,r0
mov r3,#0x64 ; mul r3,r3,r0 ; sub r3,r3,#0x1f40   ; ★ ×100 - 8000（阈值！）
cmp r3,#0 ; add r6,r3,#0xf ; movlt r3,r6 ; asr r6,r3,#4   ; ★ >>4
bl 0x8029b480 ; bl 0x8029b9dc
movt r3, #0x4059                            ; ★ 浮点常量 3.140625
str r5, [r4, #0xdc] / str r0, [r4, #0xe8]  ; ★ 写回状态
```
⇒ ⇒★★★★★ **拍照走的是【三参数加权 + 阈值判断 + 24 档动态表】**
⇒ ⇒★★★ **而取景器只走【静态 4 档】**
⇒ ⇒★★ **这就是"照片正常 / 取景器花屏"的结构性原因：两者本来就用不同的表集合！**
