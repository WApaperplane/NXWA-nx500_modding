# 「三星魔灯」实现路径分析 —— 从已知能力到可用功能

> 时间：2026-10-05 22:25
> 依据：p7 ISP 固件子系统全景（421 前缀 / 67,200 标识符）+ 三份实机验证 + libudd5 反汇编
> 目标：评估"给 NX500 加自定义胶片模拟风格"这条路的可行性并定方向

---

## 一、先说结论：★ 比想象的近，但卡点变了

**"魔灯"（自定义胶片风格注入机身）的六个必要条件，我们已确认满足四个：**

| # | 条件 | 状态 | 证据 |
|---|---|---|---|
| 1 | 固件里有正式的"风格"抽象 | ✅ **已确认** | `PW_STANDARD..PW_CUSTOM4` = 12 槽 + `NUM_OF_PW` |
| 2 | 风格参数是 7 维可调 | ✅ **已确认** | `VARIABLE_PW{PWCOLOR,PWSATURATION,PWSHARPNESS,PWCONTRAST,COLOR_R/G/B,HUE}` |
| 3 | ISP 侧有对应的处理入口 | ✅ **已确认** | `eIQ_ID_PW_{SATURATION,SHARPNESS,CONTRAST}` |
| 4 | Linux 侧有写入通道 | ✅ **已在用** | prefman 槽位 + `pw_force_reload()` enum 跳变 |
| 5 | **能装 8-bit LUT / 复杂曲线** | ⚠️ **未验证** | ISP 侧有 `LUT_Load`，但**触发路径未知** |
| 6 | **gamma 曲线可自由塑形** | ⚠️ **未验证** | 只有 `GAMMA_V`/`GAMMA_D` 两个离散档位 |

⇒ **"魔灯"的天花板取决于第 5、6 条**：
如果只能走 PW 7 参数 ⇒ 做个"富士 Velvia 味"没问题；
如果能装 8-bit LUT ⇒ **真正的胶片曲线（Halation、肩部、 toe）都能做**。

## 二、★★★ 三条候选路径（按可行性排序）

### 路径 A：PW 7 参数（**已在手，收益最快**）

**机制**（记忆里已跑通）：
```
prefman set  →  写 PW 槽位数值  →  setusr 20 0x140009 制造 enum 跳变
             →  ISP 重读 PW 段  →  风格生效
```

**7 个维度**（固件实证）：

| 固件符号 | 参数 | 记忆里的中性值 |
|---|---|---|
| `VARIABLE_PWCOLOR_R` | 红 | **100** |
| `VARIABLE_PWCOLOR_G` | 绿 | **100** |
| `VARIABLE_PWCOLOR_B` | 蓝 | **100** |
| `VARIABLE_PWHUE` | 色相 | **10** |
| `VARIABLE_PWSATURATION` | 饱和度 | **10** |
| `VARIABLE_PWSHARPNESS` | 锐度 | **10** |
| `VARIABLE_PWCONTRAST` | 对比度 | **10** |

**能做什么**：一个风格 = 7 个数。适合做
- 高饱和艳丽（Portra/Velvia 方向）
- 低对比柔和（Classic/Film 方向）
- 单色通道偏移（B 降、R 升 = 暖调）

**做不了什么**：
- ❌ 逐曲线控制（不能指定"暗部怎么压、亮部怎么滚"）
- ❌ 8-bit LUT
- ❌ 通道间串扰矩阵

⇒ **适合做"预设风格库"（5–8 个）**，不适合做"曲线编辑器"。

⚠️ **未解矛盾（必须先解决）**：记忆里 `addr(i,s) = 41964 + i*52 + s*4`，
步长 `s*4` = 1 个 u32/风格，但有 7 个参数。
**若每参数各存一份，步长该是 `7*4=28`。** 三种可能：
(a) 公式只对应某一个参数，6 个另有基址
(b) 7 个参数打包在一个 u32（每参数 4–5 bit）
(c) 公式记错了

**★ 这是路径 A 的唯一拦路虎。** 解法：`prefman` dump 原始字节，数出实际布局。
**成本极低（一次只读 dump），收益极高。**

---

### 路径 B：ISP 侧 `LUT_Load`（**上限最高，触发路径待解**）

**证据**（p7 固件 `0x714709`）：
```
LUT_Load            ★ 从 DDR 装载 LUT
LUT_ChangeAddress   ★ 换地址（多 LUT 切换）
LUT_Start / LUT_Stop
LUT_SetParam ×7     （步长 0x1c ⇒ 7 个参数化入口）
```

★★ **这是与 `libudd5.so` 的 `d5_ep_3dl_load_lut` 完全独立的第二套实现。**

| | Linux 侧（`libudd5.so`） | ISP 侧（p7 固件） |
|---|---|---|
| 入口 | `d5_ep_3dl_load_lut(addr, sel, fmt, timeout)` | `LUT_Load` |
| 通道 | `/dev/drime5_ep` ioctl + 用户态 mmap | 固件内部 |
| 当前状态 | 硬件里有 identity LUT（`0x13020619`×8） | **可能就是它自己加载的** |

**能做什么**：真正的 8-bit/16-bit LUT ⇒
- Halation（高光周围的色调溢出）
- 胶片 toe/shoulder（暗部与亮部的非线性滚降）
- 通道串扰（真正的胶片特征）
- 任意 creative LUT

**卡在哪**：
- 触发路径（谁调 `LUT_Load`？通过什么 IPC？）
- `LUT_SetParam` 那 7 个参数是什么

**★ 判断**：这条路值得走，但**必须先反汇编 `LUT_Load` 的函数体**，
看它写哪个地址、参数从哪来。**这是纯离线工作，不需要实机。**

---

### 路径 C：3×3 色彩矩阵（**★ 新发现，性价比最高**）

**证据**（p7 固件 `0x75457c`）：
```
CC_RGBL_MAT_00 .. CC_RGBL_MAT_22   (3×3, 低照度)
CC_RGBH_MAT_00 .. CC_RGBH_MAT_22   (3×3, 高照度)
```

**★ 为什么这条路性价比最高**：
- **9 个 32-bit 数 = 一个完整的调色配方**
- 立即生效（如果能写的话）
- 可回滚（改回原值即可）
- 数学上能表达：通道串扰、饱和度、色调偏移、白平衡微调

**3×3 矩阵能做什么**（用矩阵运算解释）：

| 想要的效果 | 矩阵做法 |
|---|---|
| 提升饱和度 | 通道对角线 ×1.2，行和 = 1.2（保留亮度）|
| 通道串扰（胶片特征）| 非对角线填小系数，如 R' = 1.05R - 0.03G - 0.02B |
| 暖调 | 提 R 降 B |
| 青色阴影 | 提 G/B 降 R（只影响暗部需配合 gamma）|
| 正交化白平衡 | 精确解出把光源色映射到白的矩阵 |

**卡在哪**：
- 这张表**存在固件里**（静态可见），但**谁在运行时装它**？
- 需要找到写入者（Linux 侧 prefman？还是 ISP 自己按 ISO/光源算？）

⇒ **判断**：这张表如果能被 Linux 侧影响，就是**最优雅的方案**。
下一步：**反汇编 `CC_RGBL_MAT_*` 的引用代码，找填充者。**

## 三、★ 建议路线：先 B/C 静态挖掘，再回头补 A

理由：

1. **A（PW）已经在手**，不急。**但要先解那个地址公式矛盾**（一次 dump 就行）。
2. **C（3×3 矩阵）信息量最大**（9 个数 = 完整配方），且**纯静态可挖**。
3. **B（LUT）上限最高**（真胶片曲线），且**同样纯静态可挖**。
4. **B/C 挖完之后，A 的定位也会更清楚**（三者可能是同一套管线的不同层）。

⇒ **本项目的"魔灯"应该建在 B 或 C 上，A 是保底方案。**

## 五、★ 现在就知道能交付什么

### 里程碑 1（**已具备，随时可做**）
**「5 个胶片风格预设」** —— 纯 PW 7 参数，配方库形式。
- Velvia 味：高饱和 + 硬对比
- Portra 味：暖偏移 + 中对比 + 柔锐度
- Classic 味：低对比 + 低饱和
- Mono 味：RGB 拉平 + 对比拉高
- 用户自定义：UI 暴露 7 个滑条

★ **这是"能用"的魔灯**，不需要任何新发现。

### 里程碑 2（需解 1 个矛盾）
**「精确的 PW 参数编辑」** —— 先 dump prefman 原始布局，解出地址公式矛盾，
然后每个参数都能独立精调（现在可能是打包的）。

### 里程碑 3（需静态反汇编）
**「3×3 矩阵配方」** —— 找到 `CC_RGBL_MAT_*` 的填充者，
如果 Linux 侧可影响 ⇒ 用 9 个数表达完整调色。

### 里程碑 4（需静态反汇编）
**「真胶片 LUT」** —— 找到触发 `LUT_Load` 的 IPC 命令，
支持导入 `.cube`（33³）—— **这才是真正的"魔灯"**。

## 六、风险与红线

| 项 | 评估 |
|---|---|
| ⛔ 改 p7 固件本体 | **极高**。裸镜像无封装，`st firmware up` 只吃 uImage/rom.bin，能否刷回**未验证**。动之前**必须先查上游社区** |
| ⚠️ 写 EP 寄存器 | 高。并发读风险。**只读安全，写不测** |
| ⚠️ 走 Linux UDD 通道 | **低**。这是正规 API（`libudd5.so` 公开导出），有 handle 机制 |
| ✅ 走 prefman 通道 | **低**。已在用，机制清楚 |
| ⚠️ 单核相机批量实验 | **高**。铁律：首验 1 张 1 尺寸，批量 ≤3 |

## 八、一个诚实的提醒

"三星魔灯"这个词听起来像是要改固件。**但目前最有希望的路径反而是：**
- **在 Linux 侧通过正规 API 表达你的创意**（PW 7 参数 + 可能的 3×3 矩阵）
- 而不是**去改 ISP 固件**

理由：
1. 改固件**无可靠恢复手段**（这最重要）
2. Linux 侧已有可用的写入通道
3. 3×3 矩阵 + 7 维参数**已经能表达绝大多数胶片特征**
4. 真需要 8-bit LUT 时，也应该找 IPC 触发路径，而不是改代码

⇒ ★ **"魔灯"的安全版本 = 用正规通道表达创意，
   而不是改固件。** 只有在正规通道确认无法达到目标时，
才考虑动固件 —— 而且那时必须先解决恢复问题。
