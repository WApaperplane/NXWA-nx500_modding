### L4 定性结论（不会再变的部分）

- **p7 = Cortex-A9 上的 ISP 固件**（不是 M4 裸机；M4 = LCD + 电源管理）
- **p7 的 C++ 符号名与调参键名是孤儿死数据**（4.1% 引用率）⇒ 不能用来反查参数
- **`0x4c8xxx`/`0x4ccxxx` 是 OSD/显示，不是 ISP**
- **3D LUT 是 ISP 流水线的出口，不是独立入口** ⇒ 自己塞 LUT 数据必然花屏
- **魔灯必须改 p7 —— 但理由是"LUT 数据缓冲在 p7 地址空间"，不是"写入者在 p7"**
- **`/dev/fb0` 作废、X11 作废、机身键长按/连击架构性不可得**

## 3. 关键重估：3D LUT 这条路的边际价值可能被我高估了

这是本评估里唯一需要你拍板的地方，所以单独拎出来。

**10-06 之前，"魔灯"的隐含定义是"能加载任意 `.cube` LUT"。**
但今天的发现改变了这个定义的可实现性：

```
魔灯 = 在 4 个预置缓冲间切换 + 改写缓冲内容
       ├─ 切换：用户态已通 ✅
       └─ 改写：Linux 侧不可能 ⇒ 必须改 p7 ⚠️
```

**问题**：如果改 p7 的成本是"相机变砖风险 + 每次调色都要重刷固件"，
而收益是"从 4 档变成 N 档"——那么在**已经有 9 个配方 + PW 7 维**的情况下，
**3D LUT 的边际增益是否值得动p7？**

我的判断：**不值得，除非 FilmLab 的用户反馈明确要求 tone curve。**

原因：
1. PW 7 维已经是"逐像素同值的全局向量"，能做滤镜风格（monowarm 这种机身独有能力就是例证）
2. PW 7 维**做不了**的是：tone curve / 亮度分区 / 真实 3D 色彩映射
3. 而**这才是 3D LUT 真正不可替代的地方**—— 也是唯一值得动 p7 的理由
4. 所以判据不是"3D LUT 能不能做"，而是**"用户是否真的需要 tone curve"**

⇒ **建议：在动 p7 之前，先把"魔灯到底要解决什么问题"写成一张能力矩阵。**
这张矩阵本身就是 mod 的设计文档，也是社区沟通的抓手（`docs/archive/MAGICLAMP_FEASIBILITY_2026-10-05.md`
是 10-05 的旧版，理由已被推翻，需要重写）。

**p7 改造后的形态**：
- 加一个 ioctl 或复用现有通道，接收 LUT 载荷
- p7 侧复制到目标缓冲（17³×2B = 4913 B/张，DMA 可接受）
- 只改 `CBackend_3dlut_Still.cpp` 路径 ⇒ **不影响取景器**
